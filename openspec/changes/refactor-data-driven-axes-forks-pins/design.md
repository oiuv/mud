# Design

## Context

动机见 [proposal.md](proposal.md)，来源、消费者和展示纠错见 [analysis.md](analysis.md)。三类均可复用现有 `d/items/club.lpc` 的虚拟装备生命周期；差异由原 AXE/FORK/PIN 父类提供，不需要新增行为框架。9 份来源横跨 7 个消费者，另有存取与离线路径转换，因此明确以下迁移边界。

## Goals / Non-Goals

**Goals:**

- 分别集中三类定义，保持有效蓝图/实例属性和已存在的业务入口。
- 精确处理随机装备及双手标志，验证路径替换不改变战斗分类或伐木用斧判断。
- 复用原测试与记录转换，留下可回退的基线证据。

**Non-Goals:**

- 不创建统一 weapon(kind) 解释器、全局物品注册中心、空 instance 层或任意表达式执行器。
- 不实施 SPEAR 分类调整、不修正原数值、材质和单位字段，不给物品添加新功能。
- 不扩展 NPC 领取资格、存取规则或自动保存能力，不迁移范围外物品及正式数据。

## Decisions

### 1. 三个小型 provider，沿用原父类

分别新增 axe/fork/pin 的 `.lpc` 和数据头文件，字段沿用 name、ids、weight、damage、properties；仅有实际附加标志的条目写 flags。不复用 THROWING 的叠加数量行为，也不把 PIN 并入 SWORD。独立父类比新增运行时类别分发更直接，且避免随迁移改动已验收品种。

按 `create_virtual_object(key)` 返回新克隆，驱动赋予最终身份后在 `virtual_start()` 初始化。蓝图设置固定属性并执行对应 `init_*`，实例绑定对应品种蓝图并复制可变复合值；保留物理重量、setup 次数、未知品种拒绝和重复初始化保护。

### 2. 按实际属性保留九个品种

使用 analysis.md 的简短稳定 ID，数据按 ID 自然升序。北京与铁掌的大板斧伤害/价值不同，长安板斧名称不同，不合并；同名绣花针也不能跨 PIN/SWORD 父类合并。重复输入别名可去重，原输入仍须可识别。

解析只接受本批固定初始化和明确的 TWO_HANDED 常量，复用已有 token/属性解析；原源码与 hash 不经规范化覆盖。真实驱动旧、新对象分别比较全部有效属性、默认关系、重量、权限、动作和装备行为；只放行 analysis.md 的精确展示差异。

### 3. 精确替换可达调用，不因扫描线索增加入口

6 处静态引用按 token 边界替换；长安副将只增加 `weapon_file == "axe"` 路径分支，原 random(5)、其他四个分支和技能值保持。测试使五种分支可复现，不能只靠随机多次创建碰运气。

钱正伦不在原领取白名单中接受 axe/fork，保留原文件 hash，并测试请求继续被拒绝。三家店验证完整货表及实际列货、购买和交付；三个固定携物 NPC 验证原装备语句。伐木调用真实相关函数校验斧/非斧判定，不改工作规则；隔离无关环境时在报告明确替身边界。

### 4. 存取及离线转换沿用统一入口

`feature/user_storage.c` 只追加三类 `valid_variety_path()` 检查，不允许任意虚拟对象存入。离线工具追加 9 条精确旧路径映射和基线元数据，继续覆盖既有玩家、商店、显式旧袋及 `npc/meng-zhu.o` 已授权字段。

采用临时记录验证恢复、数量、价格、幂等和新旧混合库存冲突；即使本批没有旧物品间归并，也须处理旧路径与规范路径同时出现的同一品种。正式转换仍只针对另行授权的备份，不保留运行期旧路径别名。

### 5. 复用回归，不扩大测试架构

在现有 `test_cloth_objects.mjs`、`compile_cloth_callers.mjs`、引用/记录/ID 审计入口接入三类及本批夹具；共享本批只读清单，但运行时各类保持独立。不改写历史快照消除重叠消费者断言；通过既有累计迁移适配验证最新路径。

真实驱动分开记录对象/业务回归、全库仅编译、冷/热/内存结果。三轮性能对照采用相同环境和数量，性能不是从文件数推算。用户游戏内 updateall 结果单独记录，不以离线编译替代玩家业务实测。

## Risks / Trade-offs

- [双手斧标志在解析时丢失] → 精确识别 TWO_HANDED，并验证四个双手品种与三个非双手品种的原装备结果。
- [PIN 被误当 SWORD 或 THROWING] → 保留父类、skill_type、默认动作、非叠加身份及战斗既有处理。
- [同名或数据纠错扩大范围] → 按有效属性区分九个品种，展示白名单外不改字段。
- [动态目录误开放领取] → 副将为正例、钱正伦为负例，源码及调用分别验证。
- [旧记录找不到已删除文件] → 精确映射、临时恢复和幂等验收，部署与回退同时处理代码及记录。
- [后续 SPEAR 方向混入本批] → 当前使用 FORK 原身份；独立变更再确定完整武学与存档迁移，不加过渡别名。

## Migration Plan

1. 实施获准后冻结 9 个来源、7 个消费者及保留项，采集原驱动有效属性。
2. 新增三类 provider/数据，更新实际调用、存取、离线映射与累计审计，删除本批旧定义。
3. 完成实际业务、记录恢复、历史累计回归、格式化及 --check、脚本检查和全库编译；通过后才勾选任务。
4. 记录真实性能和验证边界，同步台账与两处展示纠错的玩家日志；将 SPEAR 延后方向保留在维护文档。
5. 提交与正式部署另行确认；部署前对显式备份预览并按需转换，代码和记录配套切换、配套回退。
