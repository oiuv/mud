# Design

## Context

动机及范围见 [proposal.md](proposal.md)。以下现状已对照源码；后续结构为待实现方案。

| 位置 | 现状与需要保留的约定 |
| --- | --- |
| adm/daemons/ai_client_d.c | 环回 UDP 9999，8 KiB 字节限制，90 秒等待、5 秒后一次重传；玩家查找、等待提示和回复展示在通信层内 |
| shadow/ai.c、u/mudren/npc/butong.c、libai.c、ai_npc_template.c | 调用 send_chat_request；影子对象需要解析真实 NPC，等待提示必须保持对应名称 |
| npc_ai/src/udp_server.py | 入口直接持有 NPC、历史和记忆管理器；所有请求按 NPC/玩家字段校验，共享聊天工作池和会话锁 |
| npc_ai/src/npc_manager.py | 人设与公共模型客户端、complete_chat 混在一起；模型期限计算又依赖 knowledge_qwen |
| npc_ai/src/settings.py | 服务根目录解析路径，系统环境变量优先；REQUEST_TIMEOUT 最大 80 秒，另有聊天、摘要、检索超时 |
| NPC 持久化 | 历史、关系和 request_results 在一个事务提交；成功响应可在缓存有效期内跨服务重启去重 |
| 启动与维护脚本 | Windows/Linux 独立启停、启动前同步知识库、保留配置；游戏启动只提示 AI 服务命令 |

已有 Python 测试覆盖检索、摘要、去重、失败不落盘、超时和启动生命周期。继续作为回归基线；不以目录移动后的导入成功替代功能验证。

## Goals / Non-Goals

**Goals:**

- 公共通信不依赖 NPC；业务可明确选择响应期限和独立工作容量。
- 公共模型调用仅处理配置、请求、限时及结果错误；业务持有提示词、状态和保存策略。
- 原 NPC 调用、数据格式和用户体验保持兼容。
- 用少量清晰模块支持扩展，让无限世界只需增加业务处理方。

**Non-Goals:**

- 本次不实现世界生成、持久任务队列、场景正文、预算或发布目录。
- 不增加动态插件发现、通用工作流引擎、多进程微服务、网络协议替换或新的供应商。
- 不修改 NPC 玩法、检索算法、关系数值、数据库结构或模型默认值。
- 不向 mudcore 或 FluffOS 添加依赖。

## Decisions

### 1. 一套服务与静态业务注册

目录统一为 ai/，保留 main.py、start.bat、start.ps1、start.sh 等入口。Python 采用明确的请求类型到业务处理方映射，在服务组装处注册；仅接受本地代码登记的处理方，不通过网络指定模块名、函数名或文件路径。

建议结构：

~~~text
ai/
  main.py
  src/
    udp_server.py       # Socket, envelope, correlation, bounded dispatch
    llm.py              # Client creation, bounded completion, model errors
    settings.py
    database.py
    npc/
      service.py        # chat/memory/config, validation, session and transaction
      manager.py        # Roles, prompts, relationship rules
      history.py
      memory.py
    knowledge_basic.py
    knowledge_qwen.py
    knowledge_update.py
  scripts/
  tests/
~~~

检索模块继续保持现有职责，由 NPC 按需调用。未来世界模块接入同一注册点和 llm.py，无需构造 NPC 管理器或调用检索。拆成多个服务会增加部署和进程协调成本；动态插件机制对当前两个明确业务没有必要。

### 2. 通用 LPC 请求与薄聊天兼容入口

保留 ai_client_d.c 和 AI_CLIENT_D 宏。新增通用请求接口，输入包含请求类型、业务 mapping、结果回调及有限选项（等待时间、消息重传策略和可选回包校验）。最终签名在实现与本地 LPC 文档核对后写入客户端文档。

- 公共层生成实例唯一请求编号，复制并序列化数据，不修改调用方 mapping；业务数据不得覆盖 type/request_id。
- 立即失败与已发送请求有明确区分：提交返回含 request_id 或错误码的结果；未发送失败不再触发异步回调。已发送请求通过回调交付一个终态。
- 通信层检查服务地址、编号、响应类型和大小；NPC 可选校验函数继续检查回包 NPC/玩家身份以及正文类型。校验失败不消费待处理请求。
- 成功、超时和重载先删除待处理项及定时器，再调用业务回调；捕获回调异常，避免重入造成重复通知或容量泄漏。
- 记录调用方对象，对象销毁后不重新加载或按路径/玩家名寻找替代对象；无效回调与状态在有限期限内清理。
- 保留消息重传与业务重试的区别：底层重传相同 request_id 和序列化内容；后台任务的新一次状态查询可用新编号，持久内容去重属于业务模块。
- NPC 默认等待 90 秒，5 秒后最多重传一次；其他处理方可使用更短期限或关闭底层重传，所有值有界且重传不能越过截止时间。
- 使用总量上限与按业务容量限制。重构先保持 NPC 最多 64 个待处理请求；未来世界所需容量在其变更中配置，不能靠无限扩大通用表解决积压。

新增 adm/daemons/ai_npc_d.lpc（宏 AI_NPC_D）负责原玩家校验、同玩家/NPC 防重复、等待提示和回答展示。现有 send_chat_request() 仅向该模块转发原参数及原始调用对象；显式传递原始对象，避免中转后 previous_object() 变成通信守护程序而显示错误 NPC 名称。

保留薄入口可让四个已有调用方继续工作；新增 AI 业务直接使用通用请求接口。通信层不增加各业务的 if/else 或新的玩家输出。

### 3. 沿用消息格式，分发前只校验公共字段

保留平铺 JSON 的 type/request_id 与业务字段，现有 chat/memory/config 的请求及响应格式不更名、不套新一层 payload。缺少 type 或 request_id 的现有 Python 调用继续按默认聊天和自动编号处理；游戏通用接口始终显式发送两者。

公共错误仍使用 type=error、code、error、request_id。已知 NPC 请求可保持原 npc_id/player_id 回显；公共路由不把它们设为必填。未知类型、错误字段类型、坏 UTF-8、深度异常及超限报文在进入业务前拒绝，错误回包本身也受字节限制。

NPC service 持有角色/玩家校验、会话锁及业务处理。将现有聊天去重查询、指纹冲突检查和成功事务整体迁入，不能拆成“先写历史，再由通用层保存响应缓存”。否则进程在两个动作之间中断会导致重试重复记账。

通用入口只保留有界在途跟踪与消息关联，重传不重复调度同一正在执行的请求；复用编号但修改内容应明确拒绝。持久去重继续由业务实现，与业务写入同一事务。未来场景以 content_key 去重，不借用 NPC request_results 表。

### 4. 分开响应期限和模型期限

llm.py 提取客户端创建、实际模型调用及通用剩余时间计算；避免公共代码反向 import NPC 或知识库。调用方传入 operation（仅诊断标签）、timeout、deadline 和 max_tokens 等限制，实际超时取有限调用上限与剩余期限的较小值。

保留现有模型、端点、CHAT_EXTRA_BODY 和 SDK max_retries=0。模型未配置、超时、API 失败、空响应和截断响应以可辨别错误交给调用方；面向玩家的中文提示及离线演示由 NPC 业务决定。

保留现有环境变量名：REQUEST_TIMEOUT 的 80 秒上限仍只描述 NPC 整体请求；CHAT_TIMEOUT、SUMMARY_TIMEOUT、API_TIMEOUT 保持原行为。通用模型函数不把所有业务强制截到 NPC 的 REQUEST_TIMEOUT；未来世界调用将传入自己的后台期限。客户端按明确的所有权在服务/诊断退出时关闭。

日志保留 operation、模型、主机、耗时、错误分类和状态码，不记录 Key、提示词或 SDK 敏感异常正文。诊断脚本改用公共调用，继续支持只显示脱敏配置的模式。

### 5. 有界业务调度，场景队列留给世界变更

路由选择必须发生在 NPC 工作槽和会话锁之前。NPC 保持现有 MAX_WORKERS 容量；注册的其他处理方能够拥有自己的有界执行容量。监听循环只做短校验和投递，不同步等待模型或后台任务。

本次用测试专用处理方验证：NPC 池占满时，无玩家字段的短确认仍可返回，独立超时有效，异常释放容量。生产只注册现有 NPC 能力，不发布测试路由，也不添加未实现的 world_describe/world_status 假成功接口。

未来世界模块负责持久受理、单后台 worker、业务预算及状态查询，确认只有在任务落库后返回。世界模块同样经公共 UDP 客户端发送；场景正文仍按原无限世界方案保存到共享 JSON 目录，AI 停服时游戏可读取。共享模型账号的供应商额度仍可能相互影响，线程隔离不代表供应商配额隔离。

### 6. 路径迁移与必要文档

同步代码及活跃文档中的启动路径、日志/PID 名称、测试导入、配置示例、.editorconfig 的 PowerShell BOM 路径和 updateall 排除项。游戏 run.ps1 继续从项目目录计算 ai/start.bat，只提示独立启动。

保持服务自己的运行数据忽略规则。旧路径只在迁移说明和历史归档中出现；旧目录部署完成后由维护者清除。既不保留第二套常驻服务，也不维护永久的旧目录包装脚本。

开发文档重点解释通用请求与回调契约、类型注册、模型期限和 NPC 兼容入口；不为简单内部函数逐个增加手册。AI README 仅保留当前版本功能与使用方式，迁移和回退步骤记录在本变更中。

### 7. 与无限世界规划的分工

本变更先验收 NPC 和通用接口，再开始 add-wuxia-infinite-world。同步其提案、设计、任务及 AI 规格：

- 使用 ai/ 和公共模型入口，不再在旧 NPC 入口提前插入世界专用分支。
- 世界内容守护程序使用通用请求/回调；仅持有内容键、申请速率和同键退避等业务状态。
- 场景创建、状态查询、独立 SQLite 队列、成本限制和 JSON 原子发布均仍是世界变更任务。
- 世界地图算法、玩法要求及 M1/M2/M3 验收标准保持原规划。

## Risks / Trade-offs

- [NPC 名称因中转丢失] → 兼容入口显式传原调用对象，覆盖影子和普通 NPC 回归。
- [回包与超时/重载相邻发生] → 清理后回调，编号不复用，重复和迟到包不再次交付。
- [抽离事务破坏去重] → 保持业务成功事务完整，测试并发相同编号和重启后重传。
- [路径改名导致配置丢失或空库] → 停旧服务、核对实际数据目录、保留数据和显式路径、拒绝静默覆盖；用迁移前后样本比对。
- [旧虚拟环境含绝对路径] → 新路径重建环境；setup 不覆盖已有配置，启动托管路径同步更新。
- [抽取超时后无意放宽聊天] → 保留 NPC 80/90 秒预算及已有超时测试，另用非 NPC 假调用验证独立期限。
- [兼容层长期膨胀] → 仅保留现有聊天薄入口，后续能力统一使用通用接口。

## Migration Plan

1. 在测试目录用假模型保存重构前 NPC、UDP、存储与脚本回归基线，记录原数据路径；不运行自动真实模型测试。
2. 停止旧目录中的服务，确认目标实例已退出；备份 .env、角色配置、整个数据目录及日志。SQLite 采用停服后的完整文件副本或一致性备份，不能只复制仍在写入的主文件。
3. 部署 ai/ 代码并迁移运行数据，保留数据库文件名和内部结构；新旧目录均有数据时先确认来源，不自动合并。核对配置中的绝对路径。
4. 在 ai/ 重建 .venv 并检查进程环境变量；更新 systemd、计划任务等外部路径。迁移不主动清空索引；启动仍按原策略检查知识库并只补必要内容。
5. 在无在途对话的维护窗口更新游戏 AI 客户端和 NPC 适配层，运行项目 LPC 格式化、--check 与 FluffOS 编译，验证游戏全量编译排除 ai/。
6. 验证 Windows/Linux 启停与 status/help/logs/run 等现有命令、知识库更新、真实 UDP 假模型通信，以及 NPC 普通/影子调用。真实模型回归单独说明并显式执行。
7. 回退时停止新服务，使用保留的兼容数据恢复旧代码及其环境/托管路径；不删除新产生的聊天数据，不同时运行两套服务。

规划文件完成不代表实现通过；任务勾选以代码与对应验证均完成为准。
