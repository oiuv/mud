# Design

## Context

动机与范围见 proposal.md。代码基线为 `09e371bb`，当前 CLOTH 使用 `create_virtual_object()` 与 `virtual_start()`，数据仅包含名称、输入别名、重量和 `properties`；仓库存取只额外允许已登记 CLOTH 路径。离线转换只处理玩家仓库、玩家商店及明确选择的历史袋字段，当前必须手写清单。

只读盘点发现 `/d` 中 22 份直接 BOOTS 定义：19 份采用标准初始化、预计归并为 8 组；另 3 份麻鞋显式设置 `armor_type` 但不调用 `setup()`。HEAD 候选混有花饰及特殊回调，因此本轮只选前 19 份鞋靴，不扩大到头部防具。

## Goals / Non-Goals

**Goals:**

- 鞋靴按原行为独立成类，复用 CLOTH 已验证的虚拟生命周期、归并准则和隔离测试方式。
- 默认数据一处维护，旧来源仅进入离线基线；把声明相同与实际行为相同分开验证。
- 管理员可对指定停服备份自动盘点存档，明确知道检查了哪些文件、哪些需要转换。

**Non-Goals:**

- 不新增通用工厂、目录服务、数据库或动态注册框架；不将所有装备合成一个带类型分支的大类。
- 不修复历史麻鞋、不迁移直接 EQUIP 鞋、不改物品数值或交易限制，不新增 autoload/实例快照。
- 不自动发现正式数据目录，不读取正式存档，不负责线上覆盖、停服、备份或发布。

## Decisions

### 1. 固定一批可核对的鞋靴

下表为规划时静态核对结果，ID 为语义命名候选。实施先固定原始源码与哈希，再用真实驱动确认等价；如发现实际差异，保留品种并记录原因，不能为凑 8 个品种而合并。

| 规范 ID 候选 | 原对象路径（省略 `.c`） | 旧定义数 |
| --- | --- | --- |
| `zhanxue` | `/d/beijing/npc/obj/feet` | 1 |
| `caoxie` | `/d/city/npc/obj/caoxie`、`/d/city/obj/caoxie`、`/d/jingzhou/obj/caoxie` | 3 |
| `xiuhua_xiaoxie` | `/d/city/npc/obj/flower_shoe`、`/d/city/obj/flower_shoe`、`/d/dali/npc/obj/shoes`、`/d/fuzhou/npc/flower_shoe`、`/d/fuzhou/obj/flower_shoe`、`/d/jingzhou/obj/flower_shoe`、`/d/quanzhou/obj/flower_shoe`、`/d/yanziwu/npc/obj/flower_shoe` | 8 |
| `pixue` | `/d/city/npc/obj/pixue`、`/d/city/obj/pixue`、`/d/jingzhou/obj/pixue` | 3 |
| `qilinxue` | `/d/death/obj/qilinxue` | 1 |
| `jingzhi_xiuhua_xiaoxie` | `/d/hengyang/npc/obj/female-shoe` | 1 |
| `qingbu_sengxie` | `/d/mingjiao/obj/sengxie` | 1 |
| `shaolin_sengxie` | `/d/shaolin/obj/sengxie` | 1 |

两组绣花鞋的颜色、描述与价值不同；两组僧鞋有真实 `shaolin` 属性差异，故不合并。`shaolin_sengxie` 的门派限定来自物品属性，不是目录来源。保留历史输入别名，不为不同商店复制品种。

本轮排除 `/d/lanzhou/npc/obj/shoes`、`/d/lanzhou/obj/shoes`、`/d/village/npc/obj/shoes`：缺少 `setup()` 不能仅凭“都是麻鞋”推定初始化等价，后续单独确认。直接 EQUIP 的 `/d/city/npc/cloth/shoes` 也保持原样。相比一次迁完所有足部装备，这个范围能清楚验证已有模式的复用，不夹带行为修复。

### 2. 保留鞋靴父类，沿用已有生命周期

新增 `d/items/boots.lpc` 与 `boots_data.h`，正式身份为 `/d/items/boots/<id>`，继续继承 BOOTS。公共程序只保存定义；驱动赋名后初始化品种蓝图或克隆，设置默认对象、名称缓存、重量并只调用一次 `setup()`；可变复合属性隔离，标量按现有默认对象机制查询。

固定描述与属性只放 `properties`；不因旧源码的设置位置增加 `instance` 字段。若需要共享少量生命周期代码，仅局部复用已重复的逻辑，不借此改写全体物品继承体系。不能从 CLOTH 继承以减少代码，否则会让鞋靴获得撕布等错误能力。测试覆盖 BOOTS 的洗涤、晾干、足部槽位及性别限制，保留原材质值（含 `wood`、`boots`），不顺手“修正”数值或文案。

### 3. 迁移全部真实入口，不扩大存储权限

当前静态引用为 13 个文件的 17 处，来源于 NPC 携物与货表。动态线索已核对：

- `d/beijing/npc/qianzhenglun.c` 的 `feet` 指向本批战靴：更新该创建分支，保留领取口令、次数、门派限制、领取后 `value/no_sell` 实例覆盖，其他装备仍走原路径。
- `kungfu/class/shaolin/dao-xiang.c` 的 `sengxie` 指向本批少林僧鞋：更新对应分支，保留问询、持有判定和领取计数。
- `d/xiangyang/npc/wuxiuwen.c` 的防具列表无僧鞋；`dao-chen.c` 只发武器，不因动态拼接线索而改动。

沿用 token 级调用审计，核对新旧映射造成的键合并与数量，不仅做文本替换。`feature/user_storage.c` 只额外接受已登记的 BOOTS 虚拟品种，与 CLOTH 一起显式检查；不按任意 provider 路径动态信任对象。已穿戴、有临时状态、禁存、独特物品等资格保持，未迁移对象照旧。

### 4. 一个离线转换器，增加备份发现入口

现有转换器改名为 `tools/migrate_item_records.mjs`，保留 `--manifest`、`--driver`、`--output` 的语义与清单格式，集中使用 CLOTH 和本批 BOOTS 离线对应。旧 CLOTH 基线、404 条历史路径映射及旧报告不改写；新增 BOOTS 基线和映射，转换器不成为运行期依赖。同步现有导入、测试与当前维护文档，历史报告中的旧命令标明所属版本即可。

增加互斥的输入形式 `--backup-root <目录>`：该目录直接包含 `user/`、`shop/`，显式扫描其中普通 `.o` 文件、生成排序稳定的清单，然后复用同一预览/转换流程。不给备份目录设置默认值，不猜测 `data/`，不跟随越界链接，不递归读取其他目录。缺目录、不可读文件或链接等使检查范围不完整时明确失败并报告，不把不完整扫描输出成“无需转换”；空目录明确报告 0 文件。

可选 `--write-manifest <新文件>` 仅发现路径并保存清单，不读取存档正文或启动驱动，与转换输出模式分开；不覆盖已有清单。生成清单不代表内容检查已完成。管理员也可继续提供明确的 `--manifest`，报告须区分“备份目录发现”与“指定清单”，不把部分清单当作全库审计。

不带 `--output` 的内容检查只预览，报告覆盖范围、检查文件数、受影响文件数、各文件 `changes` 及总变更数；保留现有哈希与临时目录信息。全部选定记录验证成功且变更为 0，才可说明本次已检查范围无需转换。旧袋仍需显式 `bag_objects`，不自动加入 dbased。转换仍只产生全新的副本目录，不覆盖输入；同品同价合并库存，冲突整批拒绝，不输出误作成功的结果。

相比让维护者手填每个玩家文件，备份发现减少遗漏；相比默认扫描线上 data，它保留明确范围和停服快照边界。复用 LPC 存档解析与原字段转换，不增加第二种文本替换算法。

## Risks / Trade-offs

- [标准初始化不等于语义完全等价] → 原 19 个对象与新规范品种逐一对照；别名可归并，颜色、限制、有效属性必须保留。
- [旧动态路径或商品键遗漏] → 静态 token 审计、动态入口实测、货表数量检查和旧路径扫描共同验收；不靠保留旧壳掩盖遗漏。
- [换路径导致仓库或商店存档失效] → 临时记录验证原鞋靴、旧 CLOTH 和规范路径混用；正式上线先备份预览，按匹配版本切换代码与数据。
- [备份发现不完整被误认无影响] → 报告实际扫描范围，失败不出零影响结论；生成清单和完成内容检查分别标识。
- [虚拟创建额外开销] → 按同来源请求和相同实例数记录冷加载、热创建、内存；不预设总体更快或更省内存。
- [命令改名影响旧操作手册] → 同步当前文档与测试，明确新入口；存档格式和既有参数保持，不维护旧脚本副本。

## Migration Plan

1. 基于 `09e371bb` 保存鞋靴源码基线、哈希、规范映射和全部调用清单；旧 CLOTH 历史资料不变。
2. 在临时 MUDLIB 中验证代表品种后扩展全部 19 个旧定义，迁移调用、存取和记录转换，删除本批旧文件。
3. 完成 CLOTH/BOOTS 混合回归、自动发现与预览/副本转换测试、变更文件格式化和编译，更新维护文档。实际结果通过后才勾选任务。
4. 维护者上线时正常保存停服、备份代码与数据，更新代码及固定子模块，在备份上检查并按需生成转换副本；核对数量/价格后部署匹配记录并冷启动。不用 updateall 替代迁移。
5. 回退先停服，同时恢复匹配的代码与原记录备份；上线后的新增交易须另行核对，不把单独回退代码称为数据恢复。
