# Design

## Context

动机与影响范围见 [proposal.md](proposal.md)。当前代码基线为 `b081c7ff`，CLOTH 和 BOOTS 已有共用程序、虚拟路径、精确存取放行、离线转换和隔离驱动测试；本批沿用这条接入路径。

只读扫描在 `/d` 找到 41 个直接继承 HEAD 的文件。39 个只有 `create()`，另 2 个有相同的主人死亡销毁回调。39 个初始化定义按名称、有效属性、重量及其作用范围初步分为 36 组；该静态结论需以旧/新对象运行对照确认，不是已完成的迁移。

## Goals / Non-Goals

**Goals:**

- 在现有路径式创建、商店和存取体系内完成本批归并，不增加第二套物品身份。
- 保留实际玩家体验与有效存档数据，删除被替代的源码冗余。
- 通过完整批次对照和真实业务函数测试确定兼容性，而非只比较表内字段。
- 对已迁移 CLOTH、BOOTS、HEAD 的全部 192 个品种统一精简内部命名，保持调用简短且大致可识别物品；实际品种数与归并关系不变。

**Non-Goals:**

- 不统一改写 HEAD/EQUIP 父类，不调整历史文案、属性键、重量或物品平衡。
- 不增加通用工厂、数据文件解析框架、运行期路径别名、实例快照或自动保存功能。
- 不修改特殊死亡回调、CLOTH/BOOTS/HEAD 以外类别、mudcore、FluffOS 或 AI；不操作正式服务与正式记录。

## Decisions

### 1. 独立 HEAD 程序，沿用已验证的虚拟生命周期

新增 `d/items/headwear.lpc` 和 `headwear_data.h`，公开路径为 `/d/items/headwear/<id>`。程序继承 HEAD，提供与已有品类相同的精确路径校验和定义读取，按 `create_virtual_object(key)` / `virtual_start()` 约定在最终身份下初始化一次。

虚拟蓝图设置品种固定属性；克隆指向自身品种蓝图，复合可变属性独立复制；名称缓存、UID/EUID、派生属性及 `new(base_name(ob))` 保持正确。未指定品种的 provider 不成为可交付物品，非法路径不回退为默认品种。

不直接继承 `boots.lpc` 或 CLOTH：HEAD 的槽位和能力不同，不能为了复用初始化带入洗涤、晾干或撕布能力。当前少量相似的初始化代码不值得升级成万能物品框架；复用审计与测试辅助方法即可。

### 2. 固定属性单层，重量按实际初始化语义保留

沿用 `name`、`ids`、`weight`、`properties` 数据结构，历史别名可去重合并。规范 ID 必须简洁、唯一、有意义，优先沿用符合这些要求的已有名称；允许有意义的物品名称加稳定品种编号，如 `chahua1`、`hong_meigui2`。多词沿用 snake_case，不携带仅表示来源的地区、目录层级或作者前缀，也不强行把中文品种名或描述中的修饰词完整拼入 ID。真实门派特征可以保留。

编号区分有实际差异的品种，确定后不随数据表排序或插入而改变；等价物品仍合并为唯一 ID，不能用不同编号保留重复定义。本批内部 ID 精简如下，玩家中文名称 `name`、输入别名 `ids`、描述、属性、行为和 36 个品种的归并结果均不改变：

| 当前内部 ID | 调整后 |
| --- | --- |
| 13 个 `chahua_` 加完整品种拼音的 ID | `chahua1` 至 `chahua13`，逐一对应原茶花编号 |
| `hong_meigui_benfang` | `hong_meigui2` |
| `hong_meigui_guizhong` | `hong_meigui3` |
| `huang_meigui_hanqing` | `huang_meigui2` |

以上头饰映射保留，并将审查和实施扩展到三类全部已迁移品种。已有 `buyi`、`caoxie`、`gangkui` 等简洁名称不为统一形式而改名；长限定词改为简短物品名及稳定编号，如布衣变体使用 `buyi2`、`buyi3`，波斯教服使用 `bosi_jiaofu`、`bosi_jiaofu2`，绣花鞋使用 `xiuhuaxie`、`xiuhuaxie2`。名称只需说明大致物品，不要求编码完整颜色、重量、价格、描述或限制；真实门派等简短且实用的限定可以保留。编号映射明确保存，不按表顺序动态生成；同一类别内 ID 唯一，完整虚拟路径唯一。

玩家中文名称 `name`、输入别名 `ids`、描述、属性、行为和 CLOTH 148、BOOTS 8、HEAD 36 个品种的归并结果均不改变。正式引用、离线迁移目标、测试与维护文档同步调整，不增加运行期别名。实施结果为 CLOTH 57、BOOTS 3、HEAD 19 个 ID 精简，其余 113 个保持；明确映射保存于 `tools/tests/item_id_renames.json`。命名修订的重新验收单列在 validation.md；此前完成记录及性能报告仍属于修订前结果，不混为本轮测量。

17 份定义（13 种茶花、3 种佛山花饰、翠羽）把 `set_weight(10)` 放在蓝图分支。`feature/move.c` 将重量保存在独立的 `nosave int weight` 中，`query_weight()` 不读取默认对象的属性；静态推断这些旧克隆重量为 0，须在隔离驱动先确认。

为表达已存在的蓝图/克隆差异，数据允许可选 `clone_weight`：缺省沿用 `weight`，存在时仅指定克隆的有效重量，必须用键存在性而非真假值区分有效的 0。这属于构造元数据，不增加第二个属性 mapping，不恢复 `instance` 层。其余属性仍只由 `properties` 定义。

不将所有花饰实例统一设为 10，也不为这一个差异增加行为子类或全局重量回退。若真实驱动结果与静态推断不符，按实际旧行为调整基线和值；改变数值需另行决策，不能藏在本批重构中。

### 3. 同步实际调用，保留现有动态业务

当前扫描定位 29 个文件中的 45 处静态引用，覆盖 NPC 携物、货表、房间刷新等。实施时把调用与旧文件哈希固定为可重跑基线，替换后检查货表和刷新 mapping 是否出现归并键冲突；同品数量保留，无法无损合并的价格冲突明确报告。

钱正伦 `d/beijing/npc/qianzhenglun.c` 的 `do_yao()` 接受 `helmet`，再拼接旧路径，是本批实际动态入口。仅将该分支创建目标换为规范钢盔；保留口令、门派限制、共享护具限额、库存、领取后 `no_sell` 与 `value` 覆盖，以及已经迁移的 `feet` 分支。

其他动态线索已读源码核对：长安副将只抽取武器，道尘只发武器，武修文和道相现有护具问询不含头盔；不因它们拼接相关目录就改写。仍须扫描其他形式的路径比较和动态构造，发现真实本批调用即纳入同一清单，不扩大物品类别。

### 4. 精确存取接入，统一离线迁移

在 `feature/user_storage.c` 现有虚拟品类检查中接入表内 HEAD 路径，保留未知品种、穿戴中、临时状态、独特物品及原禁存条件；不要用宽松目录前缀替代品种校验。

为既有 `tools/migrate_item_records.mjs` 增加本批旧路径对应，不复制转换器，不改清单或输出协议。保留全部历史来源，并将已发布 CLOTH/BOOTS 旧规范路径以及本批头饰长 ID 映射到精简后的最终路径；原实体路径和第一版虚拟路径也直接到达最终路径，不依赖多次转换。一次预览/转换处理三类混合记录；历史来源仅留在测试基线和离线映射，不加载进游戏。

继续限定已有玩家、商店和显式选择的历史袋记录字段。未知字段不做全字符串替换；同品同价合并数量，冲突拒绝，新规范路径不变。默认预览、不覆盖输入、显式新目录输出副本、原字节备份及幂等性不变。命名修订重新验证三类原物品对照、实际调用编译、旧规范/新规范混合记录及重复转换；历史源码、哈希和旧结果不改写。

### 5. 先代表品种，再全批验证

代表覆盖钢盔（重复身份/动态领取）、落第秀才（蓝图/克隆重量差异）、女性限定花饰及少林头盔（真实标记）。先在临时 MUDLIB 对照原对象，再扩展全批；复用已有 CLOTH/BOOTS 测试设施，不启动正式游戏、不读取正式玩家。

测试要覆盖 HEAD 头部槽位、穿戴/卸除及实际文案、性别检查、NPC 携物、房间刷新、购买交付、存取资格、按路径重建和可变状态隔离。保留疑似历史拼写或属性键的有效行为，不把“顺手纠错”混入迁移。

性能使用旧/新隔离进程、同一组 39 个历史来源请求和相同实例数量，冷加载与热创建分别多轮测量，内存注明口径。报告绝对耗时、内存及文件数收益，不预设必须加速，也不将相对倍数单独作为否决依据。

## Risks / Trade-offs

- [只搬字段而改变花饰负重或派生属性] → 蓝图与克隆分别运行对照，显式记录重量差异，先验证再扩批。
- [按同名合并导致价格、限制或文案丢失] → 按实际定义和行为分组，合并只发生在等价候选，真实差异保留独立语义 ID。
- [漏掉动态入口或归并后 mapping 覆盖] → 审计解析引用与目录拼接，运行钱正伦原业务函数，核对货表数量和键冲突。
- [删除源码后旧记录无法恢复] → 发布前停服备份并预览，按需副本转换；代码与记录联合切换、联合回退，不保留运行期别名。
- [共享程序节省文件但增加构造开销] → 单独测量本批绝对耗时与驱动内存，结合维护收益评估，不套用前批数据。

## Migration Plan

1. 固定本批源码、哈希、等价组和调用清单，记录旧蓝图与实例实际行为。
2. 代表品种通过隔离驱动后完成全批数据、调用、存取和离线映射；删除清单内全部旧定义。
3. 完成三类混合回归、格式化与 `--check`、调用文件编译、旧路径审计及性能记录，更新维护文档和任务状态。
4. 上线由维护者在停服备份上运行统一迁移预览；零变更仅代表已核对范围，有变更则生成副本、核对后与新版代码配套切换。不是只更新代码后忽略旧记录。
5. 需要回退时恢复相匹配的代码与原始记录备份。本批开发只在临时数据上验证该流程，不代表正式服已经迁移。
