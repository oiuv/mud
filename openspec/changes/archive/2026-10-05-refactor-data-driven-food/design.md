# Design

## Context

动机及范围见 `proposal.md`，源码盘点见 `analysis.md`。现有六类虚拟物品已经提供可复用的构造、调用审计、记录转换和隔离驱动测试；本批主要差别是继承 `ITEM + F_FOOD`，不应照搬装备初始化或存放资格。

普通食物的数据差异集中在显示、重量、价格、材质、剩余食用次数及供给。食用控制在 `cmds/std/eat.c`，临时附加效果在 `feature/food.c` 的实例变量中，原物品本身没有专用食用回调。现有三份物品主规范已覆盖等价归并、行为保留和路径迁移，不修改其要求。

## Goals / Non-Goals

**Goals:** 用现有虚拟物品生命周期承载一个可独立维护的普通食物数据表，统一全部实际引用；以旧蓝图、克隆和食用行为为对照，保留正常创建、交易、刷新及资格判断。

**Non-Goals:** 不创建通用物品解释器、回调 DSL、动态注册框架或新的存档格式；不加保鲜、堆叠、自动保存等玩法。不修改 `ITEM`、`F_FOOD`、`eat` 的规则，不将 17 个特殊对象强行塞进普通类。不改正式数据、运行服务、mudcore、驱动或 AI。

## Decisions

### 1. 一个普通食物类，品种数据唯一

使用 `d/items/food.lpc` 直接继承 `ITEM` 和 `F_FOOD`，由 `food_data.h` 提供定义，正式路径为 `/d/items/food/<id>`。沿用现有 `create_virtual_object(key)` → 新克隆 → `virtual_start()`；不改 VRM，不在守护精灵里加食物分支。

无参公共对象只保管定义；有效品种在驱动赋予最终虚拟身份后初始化，蓝图保管默认属性，克隆保留原默认值回退与自身可变状态。不对外提供第二套带参商品身份，不给未知 ID 默认食物。

替代方案是保留每份旧源码为转发壳，或扩充万能物品类；前者不减少维护入口，后者引入本批不需要的复杂性，均不采用。

### 2. 按有效行为去重，不按旧路径或源码文本去重

以基线原文及真实驱动输出固定 167 份定义，生成旧路径到规范路径的离线对应。比较实际名称/颜色、描述、重量、有效属性、默认值语义及行为；等价定义合并输入别名，真实差异保留。119 个静态组只是核查起点，不是强制品种数。

ID 用物品名称的简洁拼音，允许稳定编号，如 `baozi`、`baozi2`；只有真正表达品种的限定词才保留，不拼接地区、NPC、作者等历史信息。编号不随数据排序重排；表按 ID 自然排序，调用方直接引用规范路径，不增加查表 API。

数据保持当前 `name`、`ids`、`weight`、`properties` 的简洁形态，不为大量空值增加 `instance` 层。原来未设置重量的对象按真实负重保留；缺省属性不能因统一数据格式变成不同的有效值。38 份 `setup()` 与 129 份无 `setup()` 的权限输出先做驱动对照，确认等价后统一初始化；不仅因写法不同保留冗余品种，也不凭假设改变 UID/EUID。

### 3. 食用仍交给原功能，实例状态不共享

不重写吃东西的流程。逐口食用后的 `food_remaining`、`base_value`、玩家饱食变化、`do_effect()` 和最终清除/销毁继续由原命令与功能实现。`apply_effect()` 的效果仅属于对应实例，不进入数据表、不污染同品种蓝图或另一个实例。

现有材质与状态分支照旧，包括 `plant` 分支、战斗/忙碌/饱食限制；没有明确 BUG 证据就不因名称、注释或常识修改旧数值与拼写。对一个对象吃一口后，再从规范路径及 `base_name(ob)` 创建新对象，仍获得完整的新食物。

替代方案是在新类里复写食用逻辑，会产生两套规则和回调顺序差异，不采用。

### 4. 同步引用及键合并，保留存放禁令

替换已定位的 186 处引用，并用全库静态路径审计及动态线索核对确保没有遗漏。修改实际对象路径，不改任务条件、价格、数量或业务流程。若同一 mapping 的多个旧键归并成一个新键，显式合计原数量；不同售价等冲突必须报告并解决，不让重复键静默覆盖。

背包入口只补充本表有效虚拟路径识别，使其仍到达原有“食物饮水存背包里会变质”的拒绝分支。`store all` 原有食物过滤保持，单独存放亦不成功；不能像普通装备一样把新增识别误写成新增存放功能。不开放任意虚拟对象。

### 5. 扩充既有验证和离线转换，不另建迁移系统

沿用 `tools/migrate_item_records.mjs` 的显式备份目录/清单、字段级预览、冲突拒绝、全新输出副本及幂等检查，只增加本批路径映射。旧路径对应关系只存在于离线工具与审计夹具，运行时不加载它。

食物一般不能存入背包，不据此宣称历史记录一定没有食物引用；转换临时旧记录与保持存放禁令是两项不同验收。商店同品同价库存合并数量，价格冲突保持明确失败。未选记录字段、旧有六类映射和未迁移特殊食物不受影响。

复用现有测试布局，增加本批严格清单/解析与差异审计，扩充共享驱动夹具和调用编译入口；不为这一批重写所有旧测试或建立通用代码转换引擎。

## Risks / Trade-offs

- [批量归并串品种、吞掉 mapping 条目] → 全量旧/新定义逐项对照，记录每个 ID 的成员与差异；审查同文件键碰撞、数量及价格。
- [继承顺序、缺省重量或 setup 导致实际行为差异] → 对旧蓝图和克隆采样所有定义的属性、实际负重、UID/EUID；保留行为而非机械复制写法。
- [食物状态共享或吃完不销毁] → 使用真实 `eat` 命令验证多个实例、连续食用、附加效果、清除和新建，保持特殊食物不变。
- [实体文件检查让虚拟物品提前返回] → 覆盖商店蓝图读取、购买、房间刷新、巫师 clone 和背包拒绝提示，不仅测试 `new()`。
- [共享程序热创建和内存成本增加] → 同条件对照旧/新冷加载、热创建、内存及程序数量，报告绝对值和倍率；不能把文件减少当成性能提升。
- [代码与持久路径不同步] → 停服备份后预览选定记录，有影响才转换；代码与记录一起切换和回退，不默认读取正式数据。

## Migration Plan

1. 从固定基线生成 167 份定义及引用清单、规范 ID 和原行为快照，完成真实驱动对照后落地公共类与数据表。
2. 更新全部引用、必要的虚拟品种入口检查、离线映射和测试；通过审计后删除旧定义，不保留壳文件。
3. 运行本批全量行为/调用编译/记录回归，以及既有六类、clone、village 回归；格式化所有本次修改的 LPC 并执行 `--check`。性能报告与维护文档同步。
4. 用户另行安排停服并备份代码和选定存档，用现有转换器预览。实际受影响才生成转换副本，核对后联合部署并重启，不能只拉取代码就假定旧记录兼容。
5. 如需回退，恢复与旧代码匹配的原始记录备份，不对已归并品种做猜测式逆转换；正式上线验证由部署方执行。
