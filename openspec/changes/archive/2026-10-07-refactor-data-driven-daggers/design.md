# 普通短兵器数据化设计

## Context

动机见 [proposal.md](proposal.md)，候选、预分 ID 和实际调用清单见 [analysis.md](analysis.md)。基线为 `6ad10eeeec22acc6e7190a72352b3e59c2d68840`；已有十四类采用分类 provider、规范虚拟路径及统一离线转换，本批延续既有结构。

DAGGER 初始化会添加 EDGED、SECONDARY，且父类实际装备逻辑区分主副手属性；这一点与上一批 WHIP 不同。候选中存在相同外观但不同伤害的匕首和判官笔，也有实际属于短兵器的扇、箫，必须按源码行为归类。

## Goals / Non-Goals

**Goals：**将固定初始化收敛为单份分类程序和按 ID 排序的数据，保留有效蓝图/实例数据、主副手行为及全部消费者；真实等价来源合并，纠错与玩法对照分开记录。

**Non-Goals：**不新增万能武器工厂、缓存或存档框架，不改公共 DAGGER/EQUIP、命令、虚拟分派或子模块；不迁移暗器、书籍及赤金匕首，不从名称新增毒效、演奏等能力。不读写正式数据，不自行部署。

## Decisions

### 1. 复用分类 provider，直接调用原 DAGGER 初始化

新增 `d/items/dagger.lpc`、`dagger_data.h`，沿用 `create_virtual_object(key)` 返回新克隆、驱动赋名后 `virtual_start()` 初始化的生命周期。无参 provider 只持有定义，不可当商品交付；非法/未知品种拒绝创建，调用方只使用 `/d/items/dagger/<id>`。

蓝图设置名称、重量及固定属性，调用原 `init_dagger(damage, flag)`；克隆绑定规范蓝图并隔离可变复合属性，分别保持原 `setup()` 次数、派生数值和名称缓存。最终身份、clonep、virtualp、UID/EUID 仍由驱动管理，不手动改名、赋权或双重初始化。

选择直接继承 DAGGER，而非复制其他兵器的技能和标志。候选传入 flag 均为零，但有效值为 `EDGED | SECONDARY`（6）；通过真实父类验证持用、解除、主副手转换与加成：副手不重复添加伤害等 `weapon_prop`，切换及解除时不残留属性。只保持现有规则，不借迁移修改装备算法。

### 2. 先冻结再归并，名称简短且稳定

扩展现有严格解析入口识别 DAGGER/init_dagger，拒绝额外继承、回调、动态表达式等未支持行为，不通过宽松替换把特殊物品当普通数据。冻结 23 份原文、完整消费者和排除对象 hash；在隔离真实驱动采集全部旧蓝图与克隆，再核实预分 22 组，旧十四类快照不重写。

按完整有效名称、属性、重量、伤害、标志与行为判等，不仅比较显示名。两份扬州普通匕首经驱动验证后共用 `bishou2`；荆州品种伤害不同，保留 `bishou3`。其他拟用短 ID 见清单，最终在观测通过后固定；别名可去重合并但保持旧输入可用，不追加地区或长属性前缀。数据按自然顺序排序，编号不重排。

保留原材质、单位、刚性、缺省描述和输入别名。相比为每个历史文件保留新 ID，这样消除真正冗余；相比强制合并同名物品，这样不丢玩法差异。预测品种数不作为压缩指标，观测发现真实差异须如实保留并更新清单。

### 3. 只替换实际来源，按原业务执行验收

迁移已识别 25 处静态引用，并复扫全库绝对/相对路径、宏和拼接。钱正伦 `dagger` 动态分支显式转到规范路径，保留门派、原库存与三件武器额度、实例 `value/no_sell` 覆盖及其余分支。王方平 `weapon3` 是前缀误报，不按动态入口修改。

刘素素七种扇和王方平三件短兵器使用原 F_DEALER 查询、价格、付款、交付及冷却；整张货表顺序与其他商品不变。刘素素自己只携带团扇并登记 `handing`，不改成持用。

书室继续生成毛笔 2、判官笔 1 和原 NPC，执行实际 ROOM 刷新、携走与销毁补刷。其余十二个静态 NPC 消费者中，十一处执行普通携物/持用语句；盈盈分别验证鱼肠剑空闲时取得独特兵器、已被持有时取得普通月牙匕两条原分支。保留原顺序；可用隔离替身提供无关环境，但不得以编译通过代替这些业务执行。

迁移验证后删除 23 份旧定义，不保留转发壳、运行期别名或后备旧路径。累计审计增加本批替换层；旧测试的历史货表若依赖这些文件，仅从冻结来源补入临时副本，不恢复到正式目录或改写旧快照。赤金匕首源码 hash 必须不变。

### 4. 存取和历史记录继续走已有工具

`feature/user_storage.c` 只追加合法 DAGGER 品种的精确登记判断，不接受任意虚拟路径，不放宽原拒存条件。`tools/migrate_item_records.mjs` 增加 23 条原路径到最终路径的直接映射；不新增存档字段或运行期旧身份解析。

沿用显式备份输入、默认预览、不覆盖输入的流程，范围仍为既有玩家背包、商店、显式旧袋和精确 `npc/meng-zhu.o` 的 `dbase/weapon`、`dbase/armor`。临时记录覆盖所有来源及十五类混合数据；两份扬州匕首同品同价库存合计，价格冲突整批拒绝，实例状态和无关字段保留，并验证幂等、实际恢复和原字节回退。没有实际受影响记录时不改写。

### 5. 明确文字修复，不模糊等价验收

主规范要求保留描述，用户随后明确允许纠正不影响功能的错漏。本批仅将 analysis.md 列明三处作为修复例外：北京匕首“看起来”、团扇“团扇”、荆州匕首“放回”。原名称、颜色、别名及数值仍保持。

冻结来源和旧观测保持原字节；在新定义及预期比较中按具体来源/品种和字段列出修正，验证旧文本确实存在、新文本准确，其他内容一致。不对所有输出全局替换或删掉描述比较来掩盖差异，也不加入运行期文本修复机制。同步 `help/changelog`，延续上一批已确认的“直慑九霄”，不重新改词。

### 6. 复用回归入口，独立实测性能

为现有对象、消费者编译、审计和性能入口增加 `--dagger` 及就近夹具，不另建测试执行器。覆盖全量蓝图/克隆等价、虚拟身份、一次初始化、可变状态隔离、原持用和动作、商店/房间/NPC、存取和离线恢复；保留 `/d/village`、虚拟 clone 和原十四类累计回归。

正确性测试结束后再进行三组新旧交替、每次独立驱动的性能对照；每组按 23 个历史来源各创建 20 次，共 460 实例，新实现使用同一来源映射。记录冷加载、热创建中位数、内存估算、程序数和净文件变化；不预先承诺速度或内存改善，不把内存估算当 OS RSS，也不将冷加载与未知线上热创建次数拼成总收益。

## Risks / Trade-offs

- 同名误合并 → 全量旧蓝图/克隆观测先行，22 组只是静态预估。
- 副手标志或属性计算改变 → 直接调用 DAGGER/EQUIP 并执行实际主副手转换及解除，不能只检查可克隆。
- 把扇、笔、箫当新类别 → 以实际继承和数据为准，不新增行为或“修正”材质。
- 商品和动态领取遗漏 → 对照完整消费者快照，冻结差异并复扫引用，查询线索与实际构造分开判断。
- 文案修正掩盖其他差异 → 三处精确例外单列，原文和驱动观测不改写。
- 旧存档无法恢复 → 在显式备份预览和临时恢复测试后，代码、记录配套部署与回退。
- 热创建/内存开销增加 → 独立报告实测绝对值，沿用现有结构，不为微小开销引入新框架。

## Migration Plan

1. 冻结旧定义与消费者，采集驱动观测并固定规范映射，再迁移分类程序、引用、存取和转换器。
2. 通过本类与累计回归、格式化/编译、离线恢复及性能测试后，同步开发文档、玩家文案更新和 `validation.md`；完成项只按真实证据勾选。
3. 正式部署单独执行：备份代码与相关记录，明确范围并预览；有旧身份时生成独立转换副本，核对数量、属性和价格后，在维护窗口配套部署并冷启动。
4. 回退时停止写入，成对恢复对应旧代码和转换前记录再冷启动；不能只撤销代码或恢复运行期别名。本计划不授权操作正式服务或正式玩家数据。
