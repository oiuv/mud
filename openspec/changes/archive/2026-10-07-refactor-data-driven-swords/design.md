# Design

## Context

动机和范围见 `proposal.md`，源码盘点见 `analysis.md`。已迁移七类物品提供了虚拟构造、实例隔离、引用审计、离线转换和真实驱动测试。剑类的关键差别是 `init_sword()` 只初始化蓝图，之后 `setup()` 还会生成重量和材质相关属性；不能只复制静态 set 值或直接套用食物初始化。

## Goals / Non-Goals

**Goals:** 复用现有虚拟物品生命周期，用一个 SWORD 行为程序维护固定品种，统一实际调用与历史记录转换；按旧蓝图、克隆、装备和交易行为逐项验收。

**Non-Goals:** 不创建通用武器解释器、回调 DSL、动态注册框架或第二套商品身份；不改战斗、武器平衡、权限和存取规则。不将特殊对象塞进数据表，不因表面异常修正旧行为，不新增实例快照或自动保存。

## Decisions

### 1. 一个公共 SWORD 程序，依赖最终虚拟身份初始化

新增 `d/items/sword.lpc`，继承 `SWORD`，由 `sword_data.h` 保管品种定义。沿用 `create_virtual_object(key)` 返回新克隆、驱动命名后调用 `virtual_start()` 的模式；无参公共对象只保管数据，未知品种拒绝，外部不使用带参公共程序作为另一入口。

数据保持 `name`、`ids`、`weight`、`properties` 的简单结构，加一个对应 `init_sword()` 参数的 `damage` 字段。本批全部采用默认武器标志，不预设空的 flags、instance 或行为回调字段；将来确有需要再扩展。

在 `virtual_start()` 中按最终身份初始化名称、重量和默认属性：蓝图应用定义后调用原 `init_sword(damage)`，然后执行一次原 `setup()`；克隆绑定同品种蓝图并隔离复合默认值，再执行原实例 setup。保留名称缓存、默认值回退、UID/EUID 与动作闭包行为。分支外的固定文案可归入蓝图，但先验证有效行为等价，不因存放位置不同增加 instance 层。

不选择提前初始化临时克隆，因为原 `init_sword()` 会直接返回，导致最终虚拟蓝图缺少伤害和动作。也不复制父类的战斗方法，避免两套实现长期分叉。

### 2. 按实际等价归并，用短名称维护数据

固定基线 85 份定义的原文、hash、初始化顺序、蓝图/克隆观测及对应关系。比较名称/颜色、描述、实际重量、有效属性、伤害、限制和行为；等价来源统一规范 ID、合并历史输入别名，真实差异保留。70 个静态组只是初始盘点，不能用表达式或属性写入位置的差异阻止已证明等价的归并。

ID 按物品含义命名，可用 `changjian`、`changjian2` 等短名和稳定编号，不拼接来源地区与目录层级；数据按现有自然排序规则排列，编号不随排序变化。不强行去掉具有真实游戏含义的名称限定，也不为不同商店售价复制物品。

替代方案是保留每份历史文件的身份或创建转发壳，均不能消除重复维护，故不采用。

### 3. 静态调用全量替换，动态分支只改选中的剑

迁移当前 134 处静态引用，单独处理钱政伦、长安副将和道尘的三处动态创建，保留参数、资格、持有判断、库存、随机分布与实例覆盖。其他护具和兵器分支不变，不为三处分支建立全局商品分派框架。

路径合并导致 mapping 键重合时显式保留总数量；数组重复项若承担随机权重，不去重。审计目标是所有实际引用，包括相对路径、宏拼接、任务身份判断及刷新，而不只检查 `new()` 字面量。排除对象和外部目录不扩围。

### 4. 精确接入存储，沿用离线转换边界

在背包现有精确品种检查中加入本表，不放开任意虚拟路径。原禁存、持用中、临时状态和恢复规则照旧；不新增武器耐久或附魔的完整快照能力，也不改变食物/饮具拒存。

扩展 `tools/migrate_item_records.mjs` 的离线对应，使新批次与原七类一起预览和转换。保持显式备份范围、字段级修改、数量/价格保留、同品同价库存合并、冲突拒绝、全新输出目录及幂等。旧路径仅存在于测试和离线迁移资料，不在游戏运行时加载。

不使用运行期别名兜底，也不默认读取正式玩家数据：部署时先对指定备份预览，有影响才生成转换副本。

### 5. 复用测试入口，单独覆盖武器生命周期

沿用现有 `tools/tests/test_cloth_objects.mjs`、`compile_cloth_callers.mjs` 的隔离入口，增加剑类选择与就近测试夹具、基线和审计；不另建运行框架，不重写历史快照。

全部旧/新定义比较蓝图与克隆，验证新路径重建、同品种独立性、持用/卸下、角色加成、默认动作及耐久处理。动作闭包比较实际调用结果和约定，不把闭包地址或不能 JSON 序列化当成品种差异。所有实际调用方编译，动态供应和随机配剑还需执行实际业务分支，不能以编译代替行为验收。

代表场景覆盖商店蓝图/购买、房间刷新、clone 命令、背包资格与恢复；原七类、记录转换和 village 启动回归继续通过。至少三组旧/新独立驱动性能对照分别记录冷加载、热创建、内存和程序数，给出绝对值及倍率，不把文件减少等同于性能提升。

## Risks / Trade-offs

- [克隆阶段提前初始化或重复 setup 导致伤害/派生数值错误] → 依赖最终身份初始化，逐品种对照旧蓝图与实例，并实际持用和卸下。
- [复合默认值或动作共享导致实例互相影响] → 沿用独立复合值副本；单件修改、耐久变化与后续新建均做对照，不重写继承行为。
- [归并吞掉数量、随机权重或业务差异] → 静态替换审计与三处动态分支测试分别验收；只合并经证实等价的定义。
- [特殊构造被误当普通数据] → 明确保留七件对象和源码 hash，伪金蛇剑的克隆销毁不改。
- [热创建或内存成本增加] → 实测旧/新绝对成本并记录收益边界，不以减少源文件替代运行验证。
- [代码与持久路径不同步] → 停服备份、预览、按需转换、联合切换与回退；不承诺仅 git pull 就兼容旧记录。

## Migration Plan

1. 固定基线与调用清单，采样旧行为，确定短 ID 和归并结果；实现公共程序、数据与测试。
2. 统一实际调用、精确品种识别和离线映射，删除获准替代的 85 份源码；保留七件特殊对象及其他武器现状。
3. 完成全量行为、调用编译、记录和原七类回归；对本次 LPC 执行项目格式化与 `--check`，审查差异并同步维护说明、玩家更新说明与验证报告。
4. 部署方另行安排停服并备份代码与选定存档，预览确认后按需生成转换副本，联合切换并冷启动；本批开发不操作正式服务。
5. 需要回退时恢复成对的旧代码与原始记录备份，不猜测合并后的逆向映射，不以只回退代码冒充完整恢复。
