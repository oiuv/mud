# Design

## Context

动机及范围见 [proposal.md](proposal.md)，逐物品、排除项和消费者见 [analysis.md](analysis.md)。十五类已有虚拟品种入口、精确存取检查、离线转换器及真实驱动夹具；本批复用，不引入通用物品注册中心。

THROWING 与先前 DAGGER 不同：前者继承 COMBINED_ITEM，数量是独立 nosave 字段，set_amount 重算实际重量/价值；init_throwing 与 setup 都跳过克隆。现有路径式合堆与拆分已能使用规范虚拟身份，无需另建协议。

## Goals / Non-Goals

**Goals:**

- 固定品种数据集中维护，蓝图与克隆分别保持有效属性、数量、名称缓存、UID/EUID 和最终虚拟身份。
- 等价小李飞刀统一身份；不同金镖、铁莲子和飞石仍区分。合堆、拆分、消耗和存取沿用原功能。
- 可审计地完成消费者和离线引用迁移，并持续记录未迁移物品。

**Non-Goals:**

- 不迁移 /clone，不修改暗器/叠加物公共父类、技能规则或虚拟分派。
- 不统一物品临时数据、不新增毒性保存或状态序列化，不调整商店定价、掉落数量、背包资格或玩家平衡。
- 不因本批重构清理其他分类、归档其他 OpenSpec 任务或部署正式服。

## Decisions

### 1. 单个分类程序与就近数据表

新增 throwing.lpc 直接继承 THROWING；公开入口为 new/load_object("/d/items/throwing/<id>")。沿用已验证的 provider-only 创建、未知 ID 拒绝、最终 virtual_start 初始化和重复调用保护。不会给 daemon 加暗器分支，也不允许公共程序作为可交易物品。

定义采用 name、ids、amount、damage、properties；仅确有保留需要时添加固定的初始 weight，不建立空 instance 或任意表达式执行层。数据按 ID 自然排序，历史来源只留在离线资料。init_throwing 原第二参数不生效，不将其误当有效 flag；测试仍保存原实参并验证最终 POINTED。

备选“每个旧文件保留入口”会保留重复维护；“给全部物品增加通用 kind/schema”超出本批需求，均不采用。

### 2. 按原时序初始化数量

最终虚拟蓝图先设置固定属性；克隆先绑定对应虚拟蓝图并隔离复合默认值。随后两者各自执行一次 set_amount(初始数量)，由现有父类重算重量和值；init_throwing/setup 只在最终蓝图身份下生效，调用顺序与原行为对应。公共程序 create 不提前初始化暗器，重复 virtual_start 不补满消耗量。

不把 amount 写入共享默认 mapping 代替 nosave 数量；不从 set("value") 或早期 set_weight 猜测最终值。逐项对照原蓝图和克隆，确认短刀 5400、缺 base_value 的零价值及 setup 的 no_wield 等派生结果。实例被 NPC 覆盖后再 move 时，仍遵循 combined.move 再次 set_amount 的旧规则，不保证被重算覆盖的 value 永久保留。

备选“沿用普通单件武器 setup”不能正确初始化数量与零价值，故拒绝。

### 3. 合堆与消费复用原实现

同一规范 base_name 自然合堆，等价历史小李飞刀改用同一品种后也应合堆；不同品种不合堆。new(base_name(ob)) 创建初始堆，再由 get/drop/give/put 或交易代码 set_amount 为指定数量。回归数量、总重量、价值、合并后对象销毁及失败分支的守恒，不修改这些公共命令。

本批普通暗器不带初始化毒性临时字段；六份特殊暗器保持原文。游戏后续施加的实例状态仍按旧实现处理，不借数据化更改合堆选择规则或增加保存资格。唐门暗器选取一个实际可达技能函数做新旧对照，同时验证减到零后的延迟销毁；不把模拟 add_amount 当作完整战斗验收。

### 4. 迁移消费者而非保留旧路径

冻结 41 处静态引用和钱正伦动态入口，实施时复扫全库。只替换品种路径，不更改携物数量、handing、商品顺序或奖励条件。7 个房间、2 个商店及含领取函数的 NPC 分别采用现有临时适配器执行实际相关语句/函数，并记录替身边界；编译与行为测试分开报告。

旧定义在引用切换后全部删除。引用分析命中的 weapon2 前缀不是 weapon22..25 构造，不改动。任何新增发现的真实依赖先核对并补清单，不以字面量搜索零命中声称没有动态调用。

### 5. 精确存取与离线转换

feature/user_storage.c 沿用分类程序 valid_variety_path 精确接受暗器规范路径，不放开任意虚拟对象。原记录已有 amount，恢复继续 new(path) 后 set_amount(保存数量)，不新增状态字段。无效 ID、禁存、禁售和临时状态限制保持原判断。

转换器仅增加获准 27 条旧路径到规范路径映射；复用显式备份、清单、玩家/商店/旧袋/精确盟主字段流程。验证单价与总数量不混淆、同品同价库存相加、价格冲突整批拒绝、无关字段与输入字节不变、重复转换零变化和实际恢复。原数据若含其他未支持临时状态，不在本批擅自增强恢复。

### 6. 只修明确文字错误并同步保留台账

仅应用 analysis.md 列出的三处 long 纠错，旧快照保持不变，测试预期以精确字段修正验证，不忽略全部描述差异。玩家侧更新写入 help/changelog。

维护说明新增暗器数量、合堆、初始化及使用示例；未迁移台账增加六件特殊暗器的功能、源码与保留原因，并更新分类总数和其他目录盘点。`/clone` 的登记不代表授权迁移。

## Risks / Trade-offs

- [数量操作覆盖 value/weight] → 冻结完整旧观测，分别验证创建、移动、拆分、消费和恢复的有效结果，不按源码常量强行“修复”。
- [合堆改变对象存在性] → 测试剩余对象和总数量，以规范身份预期判断等价品种合并，不依赖被销毁实例继续访问。
- [共享蓝图污染数量/复合状态] → 数量独立初始化，默认复合值独立复制，验证多实例及后续新品隔离。
- [消费者携物/持物和交易分支各异] → 保留原实际语句，按具体分支回归；不把全部暗器改成 wield。
- [热创建和内存增加] → 正确性通过后用三轮独立驱动测量27来源各20实例，报告冷/热中位数、内存与程序数，不推断未测线上总收益。
- [旧存档还指向删除路径] → 部署先做备份预览，按需转换；不得把 git pull 与重启宣称为所有存档均安全。
- [测试扩大为修复历史玩法] → 明确只兼容旧行为，发现新缺陷单列，不在迁移中暗改。

## Migration Plan

1. 确认提案后固定短兵器已提交基线、全部候选和排除项 hash，采集原蓝图/实例观测，核实归并。
2. 实现分类程序、数据和精确接入；更新消费者、离线映射及文档，删除获准旧定义，旧夹具不改写。
3. 完成独立驱动、累计回归、格式化与 --check、脚本语法、引用审计和 OpenSpec 校验，真实执行后勾选任务。
4. 用户部署时先备份代码及相关记录，运行既有离线预览，需要时转换副本并核对报告，再配套切换与冷启动；上线操作另行授权。
5. 回退使用对应版本的代码与原字节备份一起恢复，不保留运行期别名，也不只回退代码。
