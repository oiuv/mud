# Design

## Context

见 [proposal.md](proposal.md) 的动机和 [analysis.md](analysis.md) 的来源/消费者清单。基线 `487c98daa21c94bf87c732dd08c3a78123cd6685` 已有 24 张品种表和统一迁移工具，现有 HEAD/HANDS 等程序可复用生命周期。四个新增分类的父类设置各自槽位并进入 EQUIP/ITEM_D 派生初始化；共享父类不代表物品能跨类合并。

## Goals / Non-Goals

**Goals**

- 让 18 份普通定义以 10 个规范品种维护，所有旧输入别名可用，保持原蓝图/实例行为及 14 个消费者。
- 用已有虚拟身份和离线记录体系完成切换，不另建物品注册中心或配置解释器。
- 补齐四类台账，明确六份 /d 专用定义和五份 /clone 的后续边界。

**Non-Goals**

- 本批不实现容器、随机装载、死亡销毁的抽象；原专用实现继续运行，不宣称装备全部迁移完毕。
- 不修正看似不合理的材质、价格、护甲、门派限制或其他玩法；不给肚带改腰带槽、不赋予软猬甲反伤。
- 不修改正式存档、重启实服、自动推送/部署或同时推进 FORK → SPEAR。

## Decisions

### 1. 每个父类一个窄公共程序

新增 `armor/waist/surcoat/shield.lpc`，分别继承 ARMOR/WAIST/SURCOAT/SHIELD。字段沿用 `name/ids/weight/properties`，数据表按 ID 自然排序，不新增 instance 层、任意回调或通用 family 分发。比合成一个 EQUIP 程序更能直接保留槽位、extra_long 与父类行为；比每个物品保留 wrapper 更少冗余。

构造阶段只接收 provider 内部品种键，驱动确定 `/provider/key` 后再在 virtual_start 初始化。蓝图设置定义；实例绑定对应默认对象并复制 mapping/array，设置自身实际重量，执行一次原 setup。重复初始化不刷新耐久；直接克隆公共程序、未知/非法品种明确拒绝。不改驱动或 virtuald。

### 2. 按有效行为归并，不按目录保留身份

10 个 ID 及 18 条映射在 analysis.md 固定；实施先采集原对象，确认重复来源的实际结果相同再落实合并。相同牛皮盾、肚带、护腰和盘古铠共用定义；shaolin_huyao 与 tie_huyao 分开，因为门派标记确实影响售卖。跨父类同名物品不合并。若原对象实测与静态归组不符，先报告差异并调整方案，不修改冻结事实迁就预期数量。

只有两项盘古铠展示差异可放行：unit 与 long 的“见”改“件”。值、材质和输入 ID 不变；历史快照保留错误原文。

### 3. 调用只替换身份，不重写业务规则

17 处静态引用精确替换；六家商店的货表、价格/付款/冷却和四个 NPC 的装备行为不变。四个动态函数仅增加目标参数的规范路径分支，保留其余参数行为；道尘的公开 huyao 参数保留，但不新增 inquiry。钱正伦的领取计数及 value/no_sell 仍在返回实例上覆盖，不能写回蓝图。

长安副将是已核实的前缀搜索负例，不修改其五种兵器。不得将所有动态 new 都替换为本批 provider，也不增加运行期旧路径映射。

### 4. 精确存取和同一套离线迁移

在 `feature/user_storage.c` 已有品种校验链加入四个 provider；只承认注册路径，原临时数据、禁存等限制不变，不新增快照/自动携带能力。/d 六份专用物品保持原资格，不借此改容器存储规则。

`tools/migrate_item_records.mjs` 复用本批冻结映射，覆盖既有玩家、商店、显式旧袋，以及精确 `npc/meng-zhu.o` 的 `dbase/weapon`、`dbase/armor`。未知和保留物品路径不变；多旧路径及新旧混合条目若归为同品同价则合计数量，价格/数据冲突整批拒绝，绝不选一条覆盖。默认预览、输出新目录、原字节备份及幂等规则保持，不引入运行期兼容层。

### 5. 复用测试入口，保留累积证据

扩充清单/审计和现有 `test_cloth_objects.mjs`、`compile_cloth_callers.mjs`（拟新增 `--defensive-gear`），统一记录测试、ID/排序/引用检查沿用原入口；不用新执行框架。

- 冻结 18 份原文及 hash、14 个消费者，记录六份 /d 专用项、五份 /clone、四个父类、EQUIP/ITEM_D、原商店/穿戴逻辑和副将等保留依赖。
- 用真实驱动隔离副本对照 18 来源 → 10 品种。包括蓝图读取、实例派生值、槽位冲突/可并存、穿脱加减、磨损、复合值隔离、有效别名和权限。
- 商店执行真实 list/buy/delivery，售卖测试验证少林标记；领取执行原方法，NPC 执行真实 carry/wear，网络/无关技能用明确替身。
- 原 AXE/FORK/PIN 等测试曾保护钱正伦 hash；本批只用精确累计适配连接前后改动，不重写历史 baseline，不把整个消费者排除验证。
- 三轮旧/新交替进程，以同样 18 个逻辑来源加载、每来源 20 次热创建（共 360），注明旧 18 蓝图与新 10 规范蓝图的去重差异。用已有高精度计时，分别报告冷加载、每实例热创建、LPC 内存；不预设提升倍数。
- 记录实际全库/消费者编译数和警告。用户游戏内结果与隔离编译分开；此阶段不要求维护者核对虚构物品。

## Risks / Trade-offs

- [父类派生值与手抄字段不一致] → 先冻结原对象，比较 setup 后的有效状态；不只验显式属性。
- [合并少林标记或跨槽同名装备] → 分类与标记参与归组，单独测拒售和槽位。
- [公开动态参数被 inquiry 清单遗漏] → 四个函数逐项适配；副将按负例验证。
- [路径变更遗漏旧存档] → 18 条映射全部测试，无当前引用也不删映射；实服切换需先预览显式备份。
- [普通品种意外获得特殊能力] → 六份专用定义及其路径不变，并在新旧对照中检查非容器、无死亡销毁等原能力边界。
- [性能与内存增加] → 三轮实测同负载并公开绝对值，不以少量文件的收益推断实服总体延迟。

## Migration Plan

1. 冻结并验原始行为；实现四类 provider、表、消费者和离线映射，同步维护文档及未迁移台账。
2. 对合成混合记录复现 manifest/preview/copy/restore；跑对象/业务/累计回归和全量编译，填 validation.md，未验收不标完成。
3. 用户另行确认提交/部署后，按统一维护流程停服备份，对备份预览并按需转换；切换配套代码与记录，再启动验证。全量编译通过不等于无需转换存档。
4. 回退同时恢复原代码和配套记录备份；不只撤代码、不用旧路径别名弥补漏转。开发过程不操作正式记录。

无待定架构问题。实施若发现额外行为或需改变已列边界，先报告并确认；未发现的异常不靠增加通用框架预防。
