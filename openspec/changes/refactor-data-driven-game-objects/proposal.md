# Proposal

## Why

游戏已经有 ITEM/EQUIP/SWORD/NPC 等公共行为，部分品种仍重复填写属性和初始化步骤。可以用类与数据减少重复，但文件路径也承担商品、堆叠、存档等身份，不能为了合并文件再建立一套身份和兼容系统。

**改造以不增加系统复杂度为前提；需要增加复杂度的对象保持原样。** 全库盘点见 [analysis.md](analysis.md)，候选索引用于复核，不是必须完成的迁移名单。

## What Changes

- 逐类判断是否值得改造，只处理行为相同、边界清楚且能直接减少重复的对象。
- 生命周期独立、无需适配通用交易/存取等系统的对象，可直接使用 LPC 原生 `new(类路径, 参数)` / `create(参数)`；品种较多时使用类内或同目录 mapping。
- 已有路径依赖的对象保留原文件与身份，只考虑在现有行为族内提取重复初始化；若变成“原文件加数据表加转接代码”而维护更繁琐，则不改。
- 北京五把普通剑作为首个可行性对照样本，不再承诺必须改成共用程序。后续候选按类审查，允许结论是保持现状。
- 不新增全局目录服务、创建工厂、第二套品种身份、兼容别名、存档格式、缓存刷新机制或多存储后端。
- 不为参数化改造交易、合堆、拆分、仓库、自动加载、房间刷新等公共机制；特殊行为、数值和玩家文案保持原样。

## Capabilities

### New Capabilities

以下规格约束获准采用参数化/局部复用的类别，不要求全库支持统一对象数据接口：

- `game-object-definitions`：局部参数化构造与数据复用，明确有效参数、实例隔离和加载行为。
- `game-object-lifecycle`：采用新构造方式时保持既有身份、创建、交易、数量和存取契约。
- `game-object-families`：各类对象的行为保留范围与渐进接入边界。

### Modified Capabilities

无。现有正式规格未提供游戏内容目录；本方案也不要求 mudcore 采用新的数据体系。

## Impact

- 首个复核范围是 `d/beijing/npc/obj/sword1.c` 至 `sword5.c` 及剑类初始化。是否修改、是否需要局部辅助，以复杂度检查结果决定。
- 后续只按选定类别修改局部代码和数据；不预建 `object_catalog_d`、通用对象目录或全局调用适配层。
- 保留路径式物品的原文件、蓝图、创建入口与存档表达，不设置删除旧文件的迁移目标。
- mapping 优先；本次不引入 JSON/SQLite 存储接入、外部服务、驱动或 mudcore 变更。
- 2026-09-29 提交分析、候选索引与 OpenSpec 计划；2026-09-30 完成北京五把剑首批复核，按复杂度门槛保留原实现，依据见 [analysis.md](analysis.md)。后续按选定批次继续，不自动扩展为全库改造。
