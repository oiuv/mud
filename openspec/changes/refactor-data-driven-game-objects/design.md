# Design

## Context

动机见 [proposal.md](proposal.md)，数量与代码依据见 [analysis.md](analysis.md)。本游戏已有完整的继承体系，LPC 原生支持带参数的 `new()`。真正的限制是现有调用方把文件路径用作品种身份，并依赖每个品种的蓝图默认属性。

因此，“相同类加不同参数”是可选的局部简化方式，不是必须推广到所有对象的统一架构。本文件描述待实施方案，当前没有新增游戏接口。

## Goals / Non-Goals

**Goals**

- 减少真实重复，让开发者在相关行为类附近就能理解并维护一类对象。
- 保持原有属性、行为、身份、权限、存储规则与运行成本。
- 每次只做一小类；确认没有简化收益时，直接保留原实现。

**Non-Goals**

- 不追求一个品种一个数据行、全库统一 ID、删除全部品种文件或统一数据后端。
- 不新增 catalog daemon、创建工厂、对象注册层、别名迁移层、通用状态序列化、缓存刷新服务或规则解释器。
- 不改变交易、堆叠/拆分、仓库/自动加载、唯一性、房间刷新和 NPC 携物的公共接口。
- 不改传统 ROOM/AREA、特殊剧情/技能/任务、玩家自制装备、货币、驱动及 mudcore。

## Decisions

### 1. 先判断复杂度，再选择实现方式

每批用简短的前后对照回答以下问题，不另建评分系统：

| 检查项 | 可接受的变化 | 保持原样的条件 |
| --- | --- | --- |
| 内容维护 | 一处改公共步骤，品种数据就近且清楚 | 同一属性需要改多处，或多层转接才能看懂 |
| 对象身份 | 现有路径与业务身份继续有效 | 需要统一 ID、路径别名、改变品种比较 |
| 调用与存取 | 原调用和记录无需适配；独立场景只改直接调用方 | 需要联动商店、命令、仓库、自动加载等系统 |
| 生命周期 | 既有父类行为自然复用，初始化顺序明确 | 需要多种模式/兼容分支才能保住原有功能 |
| 运行与部署 | 无新增服务、逐次磁盘/数据库访问或资产迁移 | 需要维护缓存一致性、额外服务或新存档版本 |

减少行数或文件数只是辅助证据，不能抵消新增系统机制。遇到右栏条件就停止该对象的改造，不把问题转成另一个“前置基础设施任务”。即使全部候选都不适合，也允许以保留现状结束本次评估。

### 2. 两种局部方式，按实际代码选用

**A. 独立场景直接参数化**

适用于创建、使用与销毁都在同一功能边界内，且品种差异不依赖文件路径的对象。直接用 `new(类路径, 参数)`，参数可为少量明确值、mapping 或类内定义键。心魔幻境的带坐标创建是现有示例，不需要再引入虚拟寻址或工厂。

必须核对整个生命周期和所有出口：仅“在任务里创建”不够；如果对象能被带走、交易、合堆或进入现有存档，而这些通路需要额外身份适配，就不适合此方式。现有独立身份如坐标或 board_id 也不表示其整个生命周期已满足条件。

定义键只在所属类内使用，不建立全库 ID 规范、不写入通用资产记录、不与玩家别名混用。公开构造参数需要正常类型/取值检查；不让数据指定任意程序、函数或执行权限。

**B. 保留现有路径，局部提取重复代码**

适用于多个现有文件确实重复较多初始化步骤，但路径已被其他系统使用的对象。保留原 `.c` 文件、原创建方式和每个品种的蓝图；优先在已有行为族中提取一个清楚的辅助方法，参数放在原文件附近。只有实际重复足够、数据集中更易维护时才考虑小型 mapping，不要求每类都建独立数据文件。

这里的原文件仍是正式的具体对象程序，不是计划删除的过渡兼容壳。`new(旧路径)`、`base_name()`、商品蓝图读取、`new(base_name(ob))` 和存档中的 file 保持原样，不新增“旧方式/新方式”的全局分支。

必须对比完整改动：如果五个简短 create 只是被换成五个转发文件再加一张表和一个查询入口，阅读与维护反而变难，就不做。不能因为方式 B 技术上能保留路径就判定它一定值得实施。

### 3. 数据与行为保持就近

- 默认使用当前类或同目录中的 LPC mapping，保留 ANSI 宏、中文和嵌套属性；少量差异直接传普通参数即可，不强制建表。
- 不新增存储后端。JSON 和 SQLite 只是盘点中的方案比较，当前没有必须解决的外部编辑或查询需求。
- 数据只描述该类实际需要的属性，不造统一 kind/schema/任意属性执行协议。随机、条件、动作闭包和特殊效果仍写 LPC。
- 已有药品、刺青、动物等公共基类继续复用。一个品种的特殊行为可以保留在自己的文件里。
- 可变 mapping/array 在实例间保持原有隔离，必要时使用已核对的 `copy()` 深复制；只复制需要独立的状态，不把原来共享的全部蓝图属性改成每实例副本。
- 常量数据随普通 LPC 程序加载，不加集中缓存、刷新协议、自动扫描注册或热更新同步机制。

### 4. 蓝图与初始化语义

北京普通剑依赖 `set_default_object(__FILE__)`，`init_sword()` 在克隆对象上直接返回，默认伤害/动作来自各自蓝图。服饰的 armor_type 也有蓝图设置逻辑。

方式 B 必须保留这个机制。辅助代码不能把自己的 `__FILE__` 当作品种默认对象；默认对象仍指向原具体程序。不得为了参数化删除全部 clonep 判断，或使其他继承者进入新的构造模式。

`set_name()` 还维护名称缓存，装备 setup 根据重量、材质等生成衍生属性。必须保持各对象原有调用顺序、0 与未设置值、蓝图与实例的随机生成时机。没有 setup 的对象也不能顺手补一个而改变行为。

若方式 A 的某个类必须重写既有蓝图/装备逻辑才能支持多品种，优先判定不适合本批，而不是先扩展基类。合法的无参数公共程序加载与真实实例创建应分别核对，不能误建库存、移动、启动计时器或读写存档。

### 5. 类别处理结论与顺序

详细清单见分析报告。顺序表示复核优先级，不是全部必须实施的路线。

| 类别 | 首选复核方向 | 不满足条件时 |
| --- | --- | --- |
| 北京五把普通剑 | 用真实重复 create 比较方式 B 的维护成本；原属性与调用不动 | 保留五个文件及原实现；不启动交易/存档改造 |
| 普通防具、其他兵器、技能书 | 寻找足够重复的局部初始化，按已有行为族提取 | 保留路径式对象，不统一品种程序 |
| 食物、饮具 | 在保持消耗、液体状态和商店约定下判断能否局部复用 | 不为此改商店或消费流程 |
| 药材、药品、宝石、刺青 | 优先检查已有公共父类是否已经够用 | 不改叠加规则，不重复建设已存在的抽象 |
| 普通动物、简单 NPC、商人/守卫 | 仅同样行为的局部共用；只有完整生命周期独立才评估方式 A | 保留装备、掉落、归位、角色回调与路径 |
| 容器、公告板、任务物 | 先核对 contents、board_id、单例和存取行为 | 不能直接复用就保留，不列为必做迁移 |
| ROOM、唯一物、自制物、复杂剧情/技能/任务、货币 | 本次不改 | 保持现状 |

未发现值得改的候选不是实施失败。后续新增内容也按相同原则选择：有独立生命周期就自然用参数化，需要现有路径契约就继续用具体程序。

### 6. 验收与回退

每批仅需一份简短记录：涉及文件、原有重复、采用方式或保留理由、调用与状态边界、前后验证结果。无需给 4,130 个候选创建工单，也不为每种对象建立常驻测试或管理服务。

- 先做小批真实属性和行为对照；通过后再扩展同一类。
- 路径保持类重点验证原路径创建、蓝图展示、装备/使用、实际可达交易/存取。叠加物另测拆分与数量，饮具另测液体隔离，NPC 另测刷新/归位等。
- 直接参数化类验证不同参数、同参数多实例、错误参数、无参蓝图及完整生命周期；确认不会逃逸到需要新增适配的通路。
- 真实驱动验证使用隔离测试环境及临时记录，不接触玩家存档。编译通过不能代替玩法验证。
- 对修改 LPC/头文件运行项目 formatter 和 `--check`，只处理本批文件。
- 对大量创建或重置路径做同数量对象的耗时/内存对照，不预建性能平台，不以少文件宣称更快；若明显退化且只能靠额外机制补救，则放弃该改造。
- 原路径、旧记录与资格不变；回退只撤销本批代码，不需要资产格式转换。构造改动通过受控重建/重启验证，不把不重跑 create 的热更新当作初始化验证。

## Risks / Trade-offs

- [静态重复不代表语义相同] -> 核对继承、头文件、随机与副作用；只动已确认的小组。
- [共享方法扩大影响] -> 优先局部行为族，公共接口保持原语义，同时回归未改的代表对象。
- [抽取后阅读更绕] -> 比较维护一个品种和修改公共步骤所需的文件/入口；不更清楚就保留原实现。
- [对象身份仍依赖路径] -> 接受现状，不为了理想模型增加第二套身份系统。
- [可简化数量少于静态候选] -> 不设迁移数量目标，明确报告保留范围，不机械归并。

## Migration Plan

1. 本轮完成并提交规划，实施仍待维护者指定批次。
2. 首先评估北京五把剑的局部简化；记录采用或保留结论。
3. 仅对通过复杂度门槛的对象做小批实现、差异审查和相应真实驱动回归；发现需要公共系统适配就撤回该批方案。
4. 再按上表逐类选择，未选择的类别保持原样，不自动进入全库转换。
5. 文档只补实际新接口的必要用法；如果没有形成新接口，不另写一套开发手册。每批可独立结束，不引入最终“旧路径退出”阶段。
