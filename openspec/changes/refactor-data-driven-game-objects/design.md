# Design

## Context

本游戏通过 `base_name()` 区分商品、库存、订单和存档物品。直接 `new("/公共类", "品种")` 可以传参，但不同品种得到相同的 `base_name()`，无法直接沿用这些现有约定。

驱动原生虚拟对象可用一个参数化程序生成不同路径的品种，无须为每个品种保留实体文件。通用虚拟对象改造后，`adm/daemons/virtuald.c` 将 `/provider/key` 的末段原样交给父路径程序的 `create_virtual_object(string key)`；本批复用该接口，不恢复 `query_maze_room()` 分派或新增全局工厂。

首批已把 202 个旧文件逐一转换成带历史目录前缀的定义，但这只是代码集中，还保留了重复数据。此次升级以功能和数据连续性为目标，不要求保留历史文件之间的人为身份边界；旧基线用于核对，不规定最终品种数量。

## Goals / Non-Goals

- 保持实际名称、颜色、描述、数值、使用效果、装备限制、交易及存取功能；等价物品的历史输入别名可合并，不要求别名数组或源码写法逐字不变。
- 共用行为、就近维护数据，相同物品只保留一个规范 ID 和一份定义；普通品种作为同类数据中的记录维护，不再逐品种创建入口文件或保留地域副本。
- 更换路径并同步调用方；每批迁移完成必须删除全部被替代的旧物品文件。以长期维护步骤评价复杂度，不以本次需修改的文件数评价。
- 不保留旧路径转发壳或运行期别名，不提供两套正式商品身份。
- 不新增通用目录服务、工厂、状态序列化框架、规则解释器、外部服务或多数据后端。
- 不改传统地图、货币、玩家自制装备、mudcore 或驱动；其他类别按实际收益逐批选择。

## Decisions

### 1. 对外虚拟路径，内部参数化

以剑类为示意，实际目录和品种键在该类实施时确定：

```c
object ob = new("/clone/items/sword/sword1");
```

驱动通过现有 master/virtuald 找到公共程序，程序读取同类品种数据，并在内部以 `new(公共类, 品种键)` 创建对象。驱动将返回对象登记在请求的虚拟路径下。

| 行为 | 正式约定 |
| --- | --- |
| 创建 | `new(品种虚拟路径)` |
| 读取品种蓝图 | `load_object(品种虚拟路径)` 或现有路径调用 |
| 识别品种 | `base_name(ob)` 返回新品种路径 |
| 创建同品种新实例 | `new(base_name(ob))` |
| 商店、刷新与存档引用 | 继续保存一个品种路径字符串 |

直接带参创建是内部构造步骤，不作为另一种可流通商品入口。临时功能中原有的参数化对象不受此限制，但不将两种方式宣称为身份和存取等价的 API。

一个公共类代表一种共同的行为。剑、刀和只有 EQUIP 行为的服饰按实际父类区分，不将全部物品塞进带类型分支的万能类。品种键在类内唯一，不等同于玩家输入的别名。

### 2. 初始化与蓝图

依据 `fluffos/src/vm/internal/simulate.cc` 的 `load_virtual_object()`，虚拟创建回调先返回对象，驱动再设置正式对象名、clone 标志及 UID，最后调用 `virtual_start()`。不能在回调内部就假定 `base_name()` 或 `clonep()` 已代表最终虚拟品种。

实现须结合这一生命周期安排品种默认数据、`set_default_object()` 与 `setup()`，保证每个品种有自己的默认对象；不得将公共程序蓝图当作所有品种默认值。只初始化一次，不重复抽取随机值或执行装备派生逻辑。

保留 `set_name()` 缓存、属性查找语义及权限。0 与未设置、不同初始化次序若影响默认值、派生属性或实际功能，必须保持其差异；经核实无功能或数据差异的写法可统一，不把源码或内部 mapping 完全相同作为归并条件。核对 `inherit/armor/cloth.c`、`inherit/misc/equip.c`、`ITEM_D` 和 dbase，用真实驱动验证实际效果。公共程序无参加载不产生可交付物品或实例副作用；未知品种明确失败。

### 3. 数据和行为

优先使用同类就近维护的 LPC mapping，保留 ANSI 宏和中文原文，不要求 JSON/SQLite。只为实际品种定义必要字段，不建立全库 schema、统一数字 ID 或自动注册服务。

按实际属性、显示和行为识别品种：名称相同不证明物品等价，但等价物品必须合并为唯一规范 ID 和唯一数据定义，不能因原目录、文件名或来源 wizard 不同而保留副本。真实重量、价值、颜色、描述、使用效果或限制不同的物品仍分别定义；不为了合并而更改其实际效果。

普通 CLOTH 是游戏共用资产，规范 ID 使用描述物品本身的 `snake_case` 名称，例如 `buyi`、`qingbu_changshan`、`baise_changpao`；有真实差异时用能解释差异的名称，不从旧目录转换，不用来源地区、npc/obj 层级、作者前缀或无意义编号命名。地区或门派不能仅因旧文件所在位置成为 ID 的组成部分；只有确实表达物品自身特征时才作为语义限定。所有定义（包括没有重复项的定义）都须按此规范命名，不只给合并组改名。历史输入别名可去重合并并同步依赖主 ID 的调用，不作为继续保留重复品种的理由；玩家输入别名不等于旧路径运行期别名。

同品种共用定义和默认对象，但每件物品仍是独立实例；实例可变状态与默认数据隔离，不因归并 mapping 相互污染。不同商店的定价属于各自交易配置，不因此复制品种；同一商店内的归并冲突由离线迁移处理。

自定义函数若在多个物品中表达相同行为，可以形成共用子类；独有剧情、回调或权限则保留专用对象。不要仅凭有无 create 之外的函数判断能否抽取。

### 4. 现有系统接入与路径迁移

同步改实际调用方：绝对/相对路径、`__DIR__` 拼接、宏、商店货表、刷新配置、路径比较和必要的扫描入口。不能以字面量检索无命中证明没有依赖。被其他程序继承的物品必须核对继承关系后处理。

调用方全部改用归并后的规范路径，不只去重数据而继续保留多个入口。合并造成同一货表或刷新配置中路径键重合时，须核对数量与定价，不能用字符串替换后的 mapping 覆盖丢失原配置。原始文件路径及首批带目录前缀的虚拟路径只出现在历史审计、回归夹具和离线对应表中，不注册为运行期入口。

现有 `feature/user_storage.c`、`clone/misc/depot_ob.h` 及 `feature/autoload.c` 含仅接受实体 `.c` 文件的检查。对本批真实可达通路，改成正确识别受支持且可重建的物品；不能无条件放开所有虚拟对象或放宽原存储限制。未涉及的自动加载功能不顺带启用。

记录仍采用现有路径字段，不添加 definition_id/state/版本格式。旧记录的旧路径不会自动变成新路径：部署前核对受影响的仓库、库存、订单和自动加载记录，必要时提供有明确字段和适用范围的一次性转换。先用临时旧记录验证预览、备份、转换与恢复；不扫描替换任意玩家文本，不在开发测试中操作正式存档，不加入运行期旧路径查找表。

离线对应表须将原实体路径和归并前虚拟路径直接映射至规范路径，已经规范化的记录不变。背包及选定旧袋保留各记录的数量和有效属性；同一商店内等价物品且售价一致时合并库存数量，价格等无法无损归并的冲突明确报告，不选择某一条覆盖，也不发布可误作成功的转换结果。不同商店不跨店合并；输入备份不改写，重复转换应为零变更，回退仍恢复原字节记录。

切换应通过受控重启/重建完成，并处理在内存中的旧实例；不把只换程序、不重跑构造的热更新视为数据迁移。代码与持久记录一并备份和回退，不能宣称删除旧路径后只回退代码就足够。

### 5. 首批与后续

首批范围是 `/d` 下已核对的 202 个普通 CLOTH 旧定义，不扩展为新的行为族；这不是最终独立品种数量。另有 4 个带独立回调或 F_NOCLONE 的对象暂不纳入普通类。直接 EQUIP 服装另分行为族，不能因显示也是衣服而赋予 CLOTH 的撕布、洗涤能力。

先用少量代表验证新品种蓝图、创建、装备和存取，然后扩展至同类已核对品种。不同地域、不同名称的服装只要行为相同都可采用；不局限于“布衣”。其后按维护收益选择其他防具、普通兵器、食物、饮具、书籍等，不自动承诺全库迁移。

### 6. 验收

- 逐项核对迁移清单：全部被替代的旧源码已删除，运行代码及配置不再引用旧入口，也不存在转发壳或运行期别名；新品种使用共用类和集中数据，不以逐品种新文件替换逐品种旧文件。历史分析、回归夹具及一次性迁移映射中的旧路径仅作核对依据，不属于运行入口。
- 保留原 202 个定义的源码基线和旧验收记录，另外记录多对一规范映射及差异判定；验证数据表没有等价重复定义，不以一对一路径映射或固定保留 202 个 ID 验收。历史报告不冒充归并后结果。
- 用真实驱动隔离环境建立原物品与规范品种对照，验证名称、数值、原别名仍可使用、描述、穿戴、撕布、洗涤/晾干和状态隔离；允许经核对的别名合并和无语义写法统一，不要求原路径或内部数据布局相等。
- 验证两个真正不同的品种仍可区分，多个旧来源统一使用同一规范品种后各实例仍独立；覆盖蓝图展示、`new(base_name(ob))`、未知品种、已移除 ID 拒绝及公共程序无参加载。
- 实测本批实际可达的 NPC 携物、房间刷新、商店买卖、仓库存取；明确拒存规则不变，旧记录经过迁移仍能恢复对应品种与数量。
- 以临时记录验证原实体路径、归并前虚拟路径和规范路径混合输入，以及同品同价库存合并、价格冲突拒绝、数量保留、幂等和原字节回退；不为完成验收改动正式存档。
- 对相同创建负载比较耗时与内存；不以减少文件数推断性能提升，不建立性能平台。
- 对修改的 LPC/头文件执行项目 formatter、`--check` 及编译；编译通过不等于玩法验收。
- 明确测试边界，记录调用迁移和部署步骤，只补实际新接口的必要文档。

## Migration Plan

全局分类与调用链复核 → 少量虚拟品种的驱动验证 → 首批共用类和数据 → 同步引用及必要接入 → 删除旧物品文件 → 等价定义归并与规范命名 → 统一全部调用及离线迁移映射 → 隔离行为/持久记录回归 → 部署验收。任一步若只能靠新的通用框架才能保住功能，重新核对行为族或保留真正特殊的对象；不能把普通调用修改误判为系统复杂度增加，也不能以兼容为由保留无实际差异的重复定义。
