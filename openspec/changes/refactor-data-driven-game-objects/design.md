# Design

## Context

本游戏通过 `base_name()` 区分商品、库存、订单和存档物品。直接 `new("/公共类", "品种")` 可以传参，但不同品种得到相同的 `base_name()`，无法直接沿用这些现有约定。

驱动原生虚拟对象可用一个参数化程序生成不同路径的品种，无须为每个品种保留实体文件。`adm/daemons/virtuald.c` 已将非坐标路径末段交给父路径程序的 `query_maze_room()`；这是可复用的已有分派，不需要新增全局工厂。

## Goals / Non-Goals

- 保持名称、颜色、别名、描述、数值、使用效果、装备限制、交易及存取结果。
- 共用行为、就近维护数据，减少不必要的实体文件；普通品种作为同类数据中的记录维护，不再逐品种创建入口文件。
- 更换路径并同步调用方；每批迁移完成必须删除全部被替代的旧物品文件。以长期维护步骤评价复杂度，不以本次需修改的文件数评价。
- 不保留旧路径转发壳或运行期别名，不提供两套正式商品身份。
- 不新增通用目录服务、工厂、状态序列化框架、规则解释器、外部服务或多数据后端。
- 不改传统地图、货币、玩家自制装备、mudcore 或驱动；其他类别按实际收益逐批选择。

## Decisions

### 1. 对外虚拟路径，内部参数化

以剑类为示意，实际目录和品种键在该类实施时确定：

```c
object ob = new("/clone/items/sword/sword1");
```

驱动通过现有 master/virtuald 找到公共程序，程序读取同类品种数据，并在内部以 `new(公共类, 品种键)` 创建对象。驱动将返回对象登记在请求的虚拟路径下。

| 行为 | 正式约定 |
| --- | --- |
| 创建 | `new(品种虚拟路径)` |
| 读取品种蓝图 | `load_object(品种虚拟路径)` 或现有路径调用 |
| 识别品种 | `base_name(ob)` 返回新品种路径 |
| 创建同品种新实例 | `new(base_name(ob))` |
| 商店、刷新与存档引用 | 继续保存一个品种路径字符串 |

直接带参创建是内部构造步骤，不作为另一种可流通商品入口。临时功能中原有的参数化对象不受此限制，但不将两种方式宣称为身份和存取等价的 API。

一个公共类代表一种共同的行为。剑、刀和只有 EQUIP 行为的服饰按实际父类区分，不将全部物品塞进带类型分支的万能类。品种键在类内唯一，不等同于玩家输入的别名。

### 2. 初始化与蓝图

依据 `fluffos/src/vm/internal/simulate.cc` 的 `load_virtual_object()`，虚拟创建回调先返回对象，驱动再设置正式对象名、clone 标志及 UID，最后调用 `virtual_start()`。不能在回调内部就假定 `base_name()` 或 `clonep()` 已代表最终虚拟品种。

实现须结合这一生命周期安排品种默认数据、`set_default_object()` 与 `setup()`，保证每个品种有自己的默认对象；不得将公共程序蓝图当作所有品种默认值。只初始化一次，不重复抽取随机值或执行装备派生逻辑。

保留 `set_name()` 缓存、0 与未设置的区别、原初始化次序、属性查找语义及权限。核对 `inherit/armor/cloth.c`、`inherit/misc/equip.c`、`ITEM_D` 和 dbase，先做真实驱动小样验证，再扩展首批。公共程序无参加载不产生可交付物品或实例副作用；未知品种明确失败。

### 3. 数据和行为

优先使用同类就近维护的 LPC mapping，保留 ANSI 宏和中文原文，不要求 JSON/SQLite。只为实际品种定义必要字段，不建立全库 schema、统一数字 ID 或自动注册服务。

名称相同不证明行为或数值相同；数据完全相同也不自动证明原商品库存可以合并。逐个核对品种对应关系，保持必须区分的交易品种。实例可变状态与默认数据隔离，不因共享 mapping 相互污染。

自定义函数若在多个物品中表达相同行为，可以形成共用子类；独有剧情、回调或权限则保留专用对象。不要仅凭有无 create 之外的函数判断能否抽取。

### 4. 现有系统接入与路径迁移

同步改实际调用方：绝对/相对路径、`__DIR__` 拼接、宏、商店货表、刷新配置、路径比较和必要的扫描入口。不能以字面量检索无命中证明没有依赖。被其他程序继承的物品必须核对继承关系后处理。

现有 `feature/user_storage.c`、`clone/misc/depot_ob.h` 及 `feature/autoload.c` 含仅接受实体 `.c` 文件的检查。对本批真实可达通路，改成正确识别受支持且可重建的物品；不能无条件放开所有虚拟对象或放宽原存储限制。未涉及的自动加载功能不顺带启用。

记录仍采用现有路径字段，不添加 definition_id/state/版本格式。旧记录的旧路径不会自动变成新路径：部署前核对受影响的仓库、库存、订单和自动加载记录，必要时提供有明确字段和适用范围的一次性转换。先用临时旧记录验证预览、备份、转换与恢复；不扫描替换任意玩家文本，不在开发测试中操作正式存档，不加入运行期旧路径查找表。

切换应通过受控重启/重建完成，并处理在内存中的旧实例；不把只换程序、不重跑构造的热更新视为数据迁移。代码与持久记录一并备份和回退，不能宣称删除旧路径后只回退代码就足够。

### 5. 首批与后续

首批核对 `/d` 下普通 CLOTH 服装，静态分析有 202 个普通初始化候选；这不是已完成迁移的数量。另有 4 个带独立回调或 F_NOCLONE 的对象暂不纳入普通类。直接 EQUIP 服装另分行为族，不能因显示也是衣服而赋予 CLOTH 的撕布、洗涤能力。

先用少量代表验证新品种蓝图、创建、装备和存取，然后扩展至同类已核对品种。不同地域、不同名称的服装只要行为相同都可采用；不局限于“布衣”。其后按维护收益选择其他防具、普通兵器、食物、饮具、书籍等，不自动承诺全库迁移。

### 6. 验收

- 逐项核对迁移清单：全部被替代的旧源码已删除，运行代码及配置不再引用旧入口，也不存在转发壳或运行期别名；新品种使用共用类和集中数据，不以逐品种新文件替换逐品种旧文件。历史分析、回归夹具及一次性迁移映射中的旧路径仅作核对依据，不属于运行入口。
- 用真实驱动隔离环境建立原物品与新品种对照，验证名称、数值、别名、描述、穿戴、撕布、洗涤/晾干和状态隔离；原路径无需相等。
- 验证两个品种与同品种多个实例、蓝图展示、`new(base_name(ob))`、未知品种及公共程序无参加载。
- 实测本批实际可达的 NPC 携物、房间刷新、商店买卖、仓库存取；明确拒存规则不变，旧记录经过迁移仍能恢复对应品种与数量。
- 对相同创建负载比较耗时与内存；不以减少文件数推断性能提升，不建立性能平台。
- 对修改的 LPC/头文件执行项目 formatter、`--check` 及编译；编译通过不等于玩法验收。
- 明确测试边界，记录调用迁移和部署步骤，只补实际新接口的必要文档。

## Migration Plan

全局分类与调用链复核 → 少量虚拟品种的驱动验证 → 首批共用类和数据 → 同步引用及必要接入 → 删除旧物品文件 → 隔离行为/持久记录回归 → 部署验收。任一步若只能靠新的通用框架才能保住功能，重新缩小行为族或保留真正特殊的对象；不能把普通调用修改误判为系统复杂度增加。
