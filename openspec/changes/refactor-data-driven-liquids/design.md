# Design

## Context

动机与范围见 [proposal.md](proposal.md)，源码盘点见 [analysis.md](analysis.md)。现有八类物品已采用共用 `.lpc`、同目录数据表、虚拟品种路径及字段级离线转换；本批直接复用，不另建物品框架。

饮具不同于食物的关键点是：`fill` 会直接修改液体 mapping，宴席会改写名称和液体名称，`F_LIQUID` 另有实例独立的附加效果。旧定义每次构造都会重建初始液体；不能因改用蓝图而共享余量，或从已被改动的蓝图复制出错误初始液体。另有四份定义调用 `setup()`，其余没有，不能机械照搬食物的统一调用。

## Goals / Non-Goals

**Goals:**

- 用现有虚拟生命周期保持新品种路径、蓝图查询、克隆重建和有效权限。
- 固定数据集中维护，液体及附加效果仍按实例独立变化；保持原指令和业务调用顺序。
- 以冻结旧源码和真实驱动结果证明行为等价，复用已有测试及迁移工具。

**Non-Goals:**

- 不引入通用 `instance` 数据层、液体数据库、状态序列化或新的物品工厂。
- 不修改 `drink/fill/pour` 的规则，不补齐旧饮品字段、不矫正容量或酒水类型，不新增通用倒水功能。
- 不启用食物饮具背包存取，不重启正式服务或处理正式存档，不改玉蜂蜜、其他行为族和通用框架。

## Decisions

### 1. 复用 ITEM + F_LIQUID 与既有虚拟品种模式

`d/items/liquid.lpc` 继承原两个父类，以 `create_virtual_object(string key)` 返回新克隆，最终身份初始化放在 `virtual_start()`；不提前改名、提权或改 virtuald。公共程序只保存定义，无参加载不生成商品，未知品种和外部直接带参构造失败。

品种数据使用现有 `name`、`ids`、`weight`、`properties` 形式；初始液体仍是明确的 `liquid` 属性，不建立液体成分解释器。以简短数据标记保留原来是否调用 ITEM `setup()`，不把它升级为通用回调配置。蓝图和克隆分别核对原 UID/EUID。

替代方案是复制 74 个虚拟入口文件或增加统一物品 daemon，均无助于减少维护点，因此不采用。

### 2. 初始数据与当前状态分离，但不增加第二套属性体系

固定属性放品种蓝图。每次创建实例时，绑定对应蓝图并隔离可变 mapping/array；初始 `liquid` 从品种定义复制，而不是借用另一个实例或已被修改的蓝图的当前液体。原构造在默认分支后设置的 `liquid_type` 等固定值按原有效行为初始化，保持程序顺序，不用 `instance` 字段描述。

`query("liquid")` 返回实例自身的可变 mapping，使原 `fill` 修改生效。余量、改名、类型、毒效与 `F_LIQUID` 的效果变量不串实例；重复调用 `virtual_start()` 不重置已消耗余量或效果。`new(base_name(ob))` 创建原初始状态的新品，不克隆当前已消耗状态。

必须覆盖同品种两个实例、蓝图、之后新建实例及修改定义查询副本的隔离。不能用每次查询返回深拷贝的方式掩盖共享问题，那会让旧指令失效。

### 3. 按有效行为归并，不按旧目录和源码排版归并

实施前在当前基线冻结 74 份原文、hash、初始化差异、排除项和调用原文，真实驱动采集旧蓝图/克隆的有效数据。静态 54 组仅作候选，结合显示、容量、初始液体及实际功能决定最终归并。

ID 用 `jiudai`、`jiudai2`、`qingshui_hulu` 等简短名称；示例不是预先锁定所有编号。真实差异用稳定编号区分，等价定义与历史输入别名归并，顶层按自然顺序排列。`drunk_apply`、`drunk_supply`、`supply` 及缺失字段按原样保留，不统一成新的“补给”字段。

### 4. 只替换真实调用，不扩展玩法

迁移 99 处已定位静态引用，继续检查实际路径拼接、头文件和目录枚举。四处已确认不创建饮具的动态线索保持原样；如发现新实际引用，将证据加入清单，不用全局字符串替换覆盖相似路径。

- 宴席的水/酒基础对象换入口后，仍由调用方覆盖杯名、描述和液体名，保留 no_get 等属性；覆盖内容必须在移动给玩家看见之前完成。
- 厨房、茶点、商人、房间刷新保持原条件、数量和顺序；同品种货表或刷新键归并不得丢失数量和售价。
- 搜寻奖励只改四档酒袋路径，权重不变。
- 删除全部 74 个旧定义；保留玉蜂蜜原文和行为，不设置运行期旧路径兼容。

### 5. 复用存档转换，维持拒存资格

在背包原精确虚拟路径检查中登记饮具，随后仍走原食物饮水拒存分支，保持提示和 `store all` 排除行为。旧袋不重新启用，不新增自动加载或液体状态快照。

将新映射接入 `tools/migrate_item_records.mjs`，仍只转换显式备份/清单中已有获准字段。重点验证商店新旧路径混合、同价库存合计、异价冲突整批拒绝；历史背包/旧袋记录只转换已有路径及保留原字段，不把新建满液体解释为保存了旧余量。沿用已有 `npc/meng-zhu.o` 两个字段支持，不扩大 NPC 扫描范围。

与前八类混合转换，已规范路径和无关字段不变；原输入不覆盖、备份可逐字恢复、再次转换零变更。正式服是否存在旧饮具记录只能由显式范围预览决定，不因常规背包拒存便断言无需迁移。

### 6. 在现有隔离回归中验证，不新建测试平台

复用 `test_cloth_objects.mjs`、调用编译、历史引用审计和离线转换测试，增加本类模式与夹具。原食物回归复制的少林清水葫芦改用新提供程序/品种，保留旧快照用于旧版对照，不保留已删除的运行期壳。

验证分为：逐定义蓝图/克隆对照；真实 `drink/fill/pour` 及效果隔离；实际宴席、领取、刷新和搜寻调用；存取拒绝与历史记录转换；既有类别回归和修改调用编译。模拟对象仅代替无关角色/联网环境，不把实际液体和命令逻辑改成测试替身。

性能复用独立进程冷/热对照，至少三组交替顺序，报告单实例绝对耗时、总耗时、程序/对象及内存差异，不以倍率本身否定亚毫秒级开销，也不提前承诺总耗时或内存降低。

## Risks / Trade-offs

- [液体 mapping 或附加效果串实例] → 逐品种验证直接 mapping 修改、消耗、下毒、重新装水、末口清除及后续新建；不复制效果变量给新实例。
- [借重构修正旧玩法] → 旧数据和原命令为基准，特别覆盖超容量初始余量、缺失字段、末口醉酒分支及 `fill` 对既有效果的真实处理，不自行“补正确”。
- [路径合并丢失商品或奖励权重] → 静态调用清单加真实消费者回归，合并数量但保留概率，价格冲突不覆盖。
- [共享测试引用已删除文件] → 同步食物等测试依赖并重跑受影响回归，不修改历史基线掩盖回归。
- [热创建及内存增加] → 给出可复核绝对值和维护收益；仅在实测存在有意义瓶颈时优化，不增加缓存或新框架。

## Migration Plan

1. 冻结旧实现与临时驱动观测，确认品种归并和短 ID，再实现公共程序、数据及调用替换。
2. 完成隔离行为、混合记录转换、调用编译与性能验证，运行本次所有 LPC/头文件的格式化及 `--check`，记录真实结果后才勾选任务。
3. 同步维护文档及 `help/changelog`，说明玩法、存取规则不变，不向玩家暴露虚拟路径等实现术语。代码审查和提交另按维护者指令进行。
4. 部署仍采用停服备份、对明确备份范围预览、按需生成转换副本、配套更新代码与数据再重启的既有流程；本轮开发不操作正式服。
5. 回退恢复配套代码与相应原始记录，不把单独回退代码当作数据已恢复；备份与正式转换需要独立授权。
