# Design

## Context

动机与范围见 `proposal.md`，逐文件清单、父类差异和调用证据见 `analysis.md`。本库已完成十类物品数据化，具备虚拟品种、精确存取接入、离线记录转换和隔离驱动测试。本批直接 EQUIP 防具并不继承 CLOTH、BOOTS 或 HEAD，且初始化分为有/无 setup 两类，不能仅按外观复用既有服装程序。

## Goals / Non-Goals

**Goals:** 用原 EQUIP 行为加一张品种表消除普通定义文件，保持最终虚拟身份、实际默认值、原穿脱结果和持久路径恢复；沿用现有工具，减少日后维护点。

**Non-Goals:** 不设计万能装备配置框架，不新增槽位、洗涤、撕布、耐久修复或属性平衡；不为原未调用 setup 的对象自动补初始化，不修改父类、权限、存档结构或其他物品家族。疑似旧 BUG 只记录，不纳入本批修复。

## Decisions

### 1. 同一父类单独复用，不按名称换行为

新增 `d/items/equip.lpc`，直接继承原 `EQUIP`，品种数据就近放 `equip_data.h`。采用已验证的 `create_virtual_object(key)` → 驱动最终命名 → `virtual_start()` 生命周期。公共对象只持定义，未知键拒绝；外部统一 `new("/d/items/equip/<id>")`，不能直接带参克隆公共程序作为另一套商品入口。

数据只含 `name`、`ids`、`weight`、`properties` 和可选 `setup`。`armor_type`、护甲、魅力、闪避、性别及穿脱文案留在原属性中；四种槽位共用原 EQUIP 分派，不建立四个几乎相同的公共类。相较套入 CLOTH/BOOTS，此方案不引入原来没有的能力。

### 2. 显式保留 setup 选择与有效状态

25 个原调用 setup 的来源对应记录带 `"setup": 1`，其余省略。此字段只选择原无参 `setup()`，不是可配置回调或任意表达式。

最终蓝图设置名称、重量和固定属性后，按记录决定调用一次原 setup；克隆设置名称、重量，绑定品种默认对象并隔离可变复合值，再按相同记录执行一次或零次 setup。重复 `virtual_start()` 不刷新状态。UID/EUID、名称缓存、实际重量、耐久及材质缺省均与原蓝图和实例分别核对，不手动提权或补初值。

原无 setup 不应被“修正”为可穿戴：以旧对象在实际 `wear()` 和玩家 `do_wear()` 下的返回、槽位及属性变化为基准，原拒绝则新对象也拒绝。玩家命令的性别限制与 NPC 直接穿戴分别保留；文案中的历史拼写也不改。这样遵守行为兼容，而不是把函数执行成功等同于原玩法一致。

### 3. 先冻结观测，再确定短 ID

固定基线 56 份原文/hash、初始化选择、调用原文和真实驱动观测，不覆盖旧家族快照。候选解析明确支持“无 setup”或“恰好一次无参 setup”，拒绝额外函数、第二继承、动态表达式和重复调用，不采用宽松匹配吞掉未知行为。

按有效显示、属性与行为归并，历史输入别名可合并；静态 56 组仅作初始清单，不提前承诺品种数。ID 以物品自身命名，如 `magua`，有真实差异用 `magua2`，不带来源地名；其他示例为 `ruanjin_dai`、`baichou_qun`。表按自然顺序排列，编号确定后不因排序改变。不新增 instance 属性层，也不为跨店售价复制品种。

### 4. 定点替换消费者，保留历史测试语义

当前 25 个消费者中有 64 处静态引用，包含曾柔 24 项货表和 24 个其他 NPC 的 40 次配装；没有已识别的动态前缀命中。只替换实际目标，货表顺序、数量、售价、NPC 创建方法、裁缝工作条件和奖励不变；不把曾柔未销售的 `dress` 顺带加入货表。删除 56 个源文件后重扫全部路径形式，不保留兼容壳。

鞋靴旧回归曾用直接 EQUIP 绣花鞋证明不具备洗涤/撕布。本轮迁移它的路径，但继续保留该能力边界测试：当前消费者指向新品种；需要历史对照的夹具从冻结原文恢复到 OS 临时副本，不能复制已删除的当前源码。旧排除清单针对本次明确选择的对象转为核对本批迁移身份，其他排除对象仍严格检查，不能直接删除断言或改写旧快照。

### 5. 复用存储、迁移和验收入口

`feature/user_storage.c` 只增加 `/d/items/equip` 的精确 `valid_variety_path()` 检查，原穿戴中、临时状态、禁存等资格不变，不新增实例快照或开放其他虚拟对象。

`migrate_item_records.mjs` 在现有 977 条路径上增加 56 条，仍处理显式备份中的玩家仓库、商店、选定旧袋及精确盟主 weapon/armor 字段。按既有机制验证数量/价格、同价合量、冲突整批拒绝、无关字段、幂等和原字节回退，不扩大读取范围。

在 `test_cloth_objects.mjs`、`compile_cloth_callers.mjs` 增加 `--equip`，专用元数据和夹具放 `tools/tests/equip/`，不另建执行器。实际交易/穿戴/存取使用原方法，只隔离无关心跳、技能和角色环境，并报告验证边界。原十类审计与回归继续通过。

## Risks / Trade-offs

- [统一 setup 改变耐久和穿戴结果] → 逐来源记录调用选择，并在原/新蓝图、克隆及真实消费者中对照零次/一次和失败路径。
- [同名但有属性/文案差异的品种被合并] → 基于有效值和行为，而非名称，冻结原数据后确认规范身份。
- [直接 EQUIP 获得其他父类能力] → 不继承服装/鞋靴类；保留无洗涤、晾干、撕布回归。
- [删除旧鞋破坏旧家族测试] → 历史原文仅恢复到临时副本，当前消费者迁移，旧快照不变。
- [旧路径记录无法恢复] → 一次性字段级预览/转换，代码和记录同批切换及配对回退，无运行期别名。
- [每实例热创建与内存增加] → 至少三组交替独立驱动测量 56 个来源、每来源 20 次（共 1,120 实例）；报告绝对耗时、内存和程序数，不与本轮其他回归并行，不为亚毫秒开销增加缓存体系。

## Migration Plan

1. 冻结原定义、调用与实际驱动观测，确认初始化差异和短 ID。
2. 加入公共程序/品种表，切换调用、精确存取及离线映射；删除本批 56 份定义，适配受影响旧测试。
3. 完成穿脱、商店、NPC、存取、记录转换、原家族回归、调用编译与性能对照；格式化本次 LPC 并执行 `--check`，更新维护文档及适用的玩家更新说明，以验证报告记录证据。
4. 正式部署另行确认：停服备份、预览选定范围、按需转换，代码与记录配套切换后冷启动；`updateall /` 不替代旧实例清理。
5. 回退恢复对应代码和原记录；新版本运行后产生的交易须另核对，不能猜测合并前来源并全局反向替换。
