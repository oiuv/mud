# Design

## Context

范围与动机见 [proposal.md](proposal.md)，逐品种及调用表见 [analysis.md](analysis.md)。基线已经实现十八类物品迁移，虚拟路径、默认蓝图、存取检查、离线转换和隔离测试都有现成设施。

本批与普通书籍不同：24 个旧乐器都会调用 setup，并通过原 MI 继承注册 play；不能直接复制书籍的“无 setup”初始化。三个 MI 的实际演奏逻辑仍在对应技能文件内。现有四份主规范已经覆盖本次行为保持与路径迁移，不增加增量规范。

## Goals / Non-Goals

**Goals：** 集中维护固定品种数据，复用音乐能力，保持旧对象从创建到演奏、交易和恢复的有效行为；数据与运行期身份只保留一份。

**Non-Goals：** 不新增音乐玩法，不把武器改成普通乐器，不开放原不能演奏的外观物品，不修正音乐等级或效果规则，不新增自动保存，不引入通用执行数据或第二套工厂。

## Decisions

### 1. 三个小 provider，保持静态继承

- `qin.lpc`：ITEM + MI_QIN，`qin_data.h` 存放 15 个品种。
- `xiao.lpc`：ITEM + MI_XIAO，`xiao_data.h` 存放 7 个品种。
- `zheng.lpc`：ITEM + MI_ZHENG，`zheng_data.h` 存放 2 个品种。

每类沿用原 `init()` 的 play 注册方式，不新增命令分派器。不采用“所有乐器都继承三个 MI，再靠配置开关禁用”的单类方案，否则对象会获得原来没有的 valid_as_* 能力。也不为只省少量初始化代码增加新的通用基类或工厂。

分类依据实际继承；胡琴仍使用原 MI_QIN，不按现代乐器学另改技能。

### 2. 原生虚拟生命周期与简明数据表

沿用既有 `create_virtual_object(key)`、`virtual_start()`、`query_definition()`、`valid_variety_path()` 约定。公共程序保存品种定义，返回新克隆交给驱动赋予虚拟身份；最终身份确定后初始化一次。

品种数据只需 name、ids、weight、properties；不引入空 instance 字段、运行期旧路径映射或可执行表达式。蓝图保存固定属性，实例绑定同品种蓝图；复合可变属性按已有实现隔离。set_name、set_weight、默认对象与 setup 的相对顺序按旧程序保留，并分别比较蓝图/克隆实际值。重复初始化不重复 setup，不重置已改变的实例状态；无参公共程序、未知 key 不成为可交付物品。

内部短 ID 见分析表，按自然顺序维护。两个胡琴和三个竹萧因真实差异使用稳定编号；流银琴等不因同价就合并，不改变玩家显示、别名或描述。若真实驱动发现静态扫描遗漏的等价项，按既有归并标准核验并同步清单，不机械保留重复定义。

### 3. 复用演奏，不重写演奏

保留原 `play <曲名>` 和 `play <曲名> with <物品别名>`。原 MI 回调负责对象别名匹配并转交对应技能，provider 不复制其门槛、输出、忙时和曲谱效果。

测试比较旧物品与新物品的真实 action 注册及 MI/技能调用：无参数、错误别名、缺曲谱、不适配曲谱、忙碌、成功与等级档位；同时持有多个乐器时验证原命令选择行为。成功演奏仍调用一次原 do_effect，最低档也如此。采用实际技能实现及可观测曲谱/玩家替身控制输入时，记录替身范围，不把替身测试称为真人端到端验收。

### 4. 更新使用者，不扩展游戏内容

替换分析表的 27 处引用，保留 11 个使用者的其余逻辑：

- 两个商店的货品顺序、价格和购买数量；绯胭三本自定义书仍用原实现，不给她增加原未售的檀木胡琴。
- 武器库的刷新数量及 replace_program；道具房三条随机分支的分布与伴随物品。
- 六位 NPC 的 handing 临时对象和欧阳锋的铁筝携带；不顺带把乐器 wield 或增加属性。
- 副将动态 weapon_file 的五个候选均非本批乐器，维持源文件不变。

引用审计包含可解析字面量、相对路径、__DIR__ 拼接及动态前缀；通过后删除 24 份旧文件。不使用运行期转发壳兜底漏改引用。

### 5. 存档仍用原记录协议

在 `feature/user_storage.c` 复用精确 provider + 品种检查，不因虚拟对象都无实体文件就全部允许。普通乐器按旧存取资格恢复；其他拒存条件、武器乐器和特殊对象不改变。

统一 `tools/migrate_item_records.mjs` 增加 24 条原路径到新品种映射，复用既有玩家、商店、显式旧袋和精确盟主字段协议，不增加扫描范围。默认预览，输入只读，输出全新；保留数量、价格、未知字段、幂等与冲突拒绝。即使本批没有归并，也继续跑累计同品同价合计和价格冲突回归。

### 6. 扩展原测试设施，分别报告正确性与性能

冻结基线原始源码、真实 hash、品种表、消费者和保留项，不使用解析器规范化后的源码 hash 冒充原始 hash。接入现有隔离驱动测试入口，新增本批夹具与审计，沿用既有十八类回归，不另建执行框架。

除了字段对比，覆盖 clone/load/default identity、UID/EUID、实例隔离、实际演奏分支、list/buy、房间刷新、NPC 携带和真实 store/qu。源码删除后的旧对象仅从冻结快照恢复到隔离副本。

对修改的 LPC/头文件格式化并 --check，再运行消费者编译和全量 LPC 零警告检查。至少三轮独立驱动对照冷加载、热创建、内存和程序数，报告绝对量与文件数量，不能仅凭百分比判定游戏体验。

## Risks / Trade-offs

- **同名乐器误归类或误合并** → 比较继承、有效属性、别名及行为；武器/XSWORD 负例保留 hash。
- **setup 或默认对象时序改变重量/属性** → 分别冻结旧蓝图与克隆并在最终虚拟身份阶段对照，不套用书籍无 setup 的特例。
- **多件乐器的 action 顺序变化** → 测原 play 入口与 with 别名选择，不只直接调用 play_*。
- **只编译成功但商品或存档引用失效** → 实际消费者执行、旧路径扫描及临时记录恢复独立验收。
- **共用数据增加常驻内存或单次创建开销** → 测量绝对值；允许为可维护性付出合理小开销，不承诺迁移会让所有指标更快。
- **三小类保留少量重复结构** → 用来保证原生能力边界；本批不为消除这些代码引入更复杂抽象。

## Migration Plan

1. 固定分析清单和旧运行结果，完成三个 provider/数据表、消费者迁移及精确存取接入。
2. 完成全部回归后移除旧文件，同步物品总览、乐器维护说明、未迁移台账和 help/changelog；台账注明特殊演奏武器、/clone 暂缓与范围外外观物品，交叉归属按路径去重。
3. 审查测试与差异，用户确认后提交。实施阶段不读取正式存档、不停服、不调用 AI、不自动推送。
4. 部署时由管理员安排停服，备份匹配版本代码与记录；对显式备份副本执行统一预览/转换，部署完整成功的输出后重启。范围不全或预览失败不能报告“无需转换”。
5. 回退同时恢复旧代码及对应原始记录；不能仅撤回代码却留下新虚拟路径。正式环境结果与隔离结果分开记录。
