# Design

## Context

动机与实施范围见 [proposal.md](proposal.md)，逐物品及消费者依据见 [analysis.md](analysis.md)。当前十六类已有虚拟品种、精确存取、离线转换及真实驱动夹具；CLUB 可沿用普通杖/剑的装备初始化方式，不沿用上一批暗器的叠加数量逻辑。

## Goals / Non-Goals

**Goals:**

- 使用既有虚拟生命周期集中维护棍类定义，保持品种身份、有效属性、装备和旧记录恢复。
- 等价齐眉棍共用一份数据；扫描动态目录前缀后按实际调用条件迁移，不凭线索新增能力。
- 在明确的展示纠错之外，逐项保存原蓝图、克隆和消费者业务结果。

**Non-Goals:**

- 不建全局品种注册中心或统一武器解释器，不修改 CLUB/EQUIP/F_EQUIP、虚拟分派和技能。
- 不扩展 NPC 询问词、调整门派/师承/库存/价格，不按文案修正可疑材质或数值。
- 不迁移范围外物品、不归档其他任务、不操作正式存档或部署游戏。

## Decisions

### 1. 复用既有分类程序结构

以 `d/items/staff.lpc` 的小型 provider 模式新增 CLUB 分类，数据字段为 name、ids、weight、damage、properties，只有实际非零标志才需要 flags。固定数据自然排序，不增加空 instance 层、任意表达式或新的配置语言。

公共程序仅提供品种查询/创建；`virtual_start()` 在驱动给定最终身份后初始化一次。蓝图写固定属性并执行 init_club，克隆绑定对应默认蓝图并复制可变复合值，分别保留重量及 setup。未知 ID、公共程序直接构造和重复初始化按现有契约拒绝或保护。

不使用暗器的 set_amount，不用通用 kind 分支代替独立父类。逐文件壳会保留冗余，改公共父类则扩大风险，均不采用。

### 2. 有效行为决定归并

严格解析只接受本批 18 份单父类、固定初始化，冻结原文/hash；蓝图/克隆真实观测确认 17 个品种及齐眉棍归并。父类生成的 LONG、动作、躲闪、材质派生和 UID/EUID 一起核对，不只比较构造文本。

主副手行为由原 F_EQUIP 决定；LONG 不增双手要求，钢材木棍、丝质长枪等原数据保留。display 纠错使用 analysis.md 的精确字段转换，不忽略全部字符串或改写历史基线。

### 3. 动态函数只替换既有可达路径

27 处静态引用按 token 边界替换。道尘 ask_me 明确增加 qimeigun 的规范路径分支；道相、武修文的公开 ask_me_1 原本也能由入参创建该路径，增加同样精确分支保留函数契约，但 inquiry 不变、不注册新口令。三者原门派、持有检查、库存和其他分支分别验证，不统一成一个新发放器。

钱正伦在目录拼接前明确拒绝 mace/club，因此不加分支、不改白名单；保留其源码 hash，并验证仍拒绝。将所有目录命中一律替换会误扩权，仅改玩家注册入口则会遗漏公开函数的原行为，均不采用。

张乘风构造和 ask_gun 保留唯一神木的原获取/归属/交付流程，只迁移备用熟铜棍路径和指定对话错字。神木本体、hit_ob 和克隆销毁不迁移。测试可用简单对象隔离神木的战斗本体，但必须执行原持有判断、give 和后续装备；不得将替身测试说成完整唯一武器或战斗验收。

### 4. 商店与存档沿用同一正式身份

三家商店保持完整货表、顺序和原交易函数；F_VENDOR 实际就是 F_DEALER，不另外适配历史 vendor.c。新虚拟蓝图与实例使用相同规范身份，不增加第二种商品 key。

`feature/user_storage.c` 只增加 club 分类的 valid_variety_path 检查。离线转换器只追加 18 条映射和基线元数据；玩家、商店、显式旧袋及精确盟主字段继续复用现有流程。两份齐眉棍遇同价库存合计、异价冲突仍拒绝，存取数量、无关字段和原字节回退不变，不增加运行期别名。

### 5. 按批次保留验证证据

复用现有 `test_cloth_objects.mjs`、`compile_cloth_callers.mjs`、引用/ID/记录工具，增加 `--club` 及本批小型夹具，不另造测试框架。三家店、17 个普通 NPC 携物语句、三个动态函数、张乘风业务分别运行实际相关函数；无关角色基础设施可以隔离，报告替身边界。

旧十六类夹具的已删除依赖只从冻结快照恢复到临时副本，累计审计逐批核对允许差异，不改写旧快照来消除失败。没有本批房间陈设引用，保留既有村庄/虚拟 clone 回归，不新增虚构刷新验收。

## Risks / Trade-offs

- [同名/描述容易诱导改功能] → 显示与内部类别分开，保留原字段、派生属性及主副手限制；只做指定展示纠错。
- [共享默认对象污染实例] → 复合值独立复制，回归注册表、蓝图、两个实例及后续创建的隔离。
- [动态前缀误判为玩家入口] → 按实际参数检查、公开函数及 inquiry 分别核对，钱正伦作为负例。
- [齐眉棍归并覆盖库存] → 离线转换维持同价合计、冲突拒绝、幂等；不以保留重复 ID 绕过问题。
- [旧记录引用被删除文件] → 部署先预览备份并按需转换，代码和记录配套切换/回退；编译成功不代表所有存档安全。
- [热创建或内存增加] → 正确性通过后用 360 实例、三轮独立驱动测量冷/热/内存与程序数，不用文件数代替性能证据。

## Migration Plan

1. 方案确认后冻结提交、18 个来源和 24 个消费者、保留项 hash，采集旧对象有效观测。
2. 实现分类程序/数据，更新消费者、精确存取及离线映射，删除获准旧文件；同步台账、架构说明和玩家文字纠错。
3. 完成实际业务、十七类累计和记录恢复回归，格式化本次 LPC 并运行 --check、脚本语法和 OpenSpec 严格检查；实际通过才勾选。
4. 独立驱动完成三轮性能对照并记录 validation.md。用户全量编译与离线检查分别记录，不预报实测数量。
5. 提交/上线另行确认；正式部署仅处理已批准备份范围，保留原字节。回退对应代码与记录，不保留运行期旧路径。
