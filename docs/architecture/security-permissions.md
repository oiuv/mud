# 简化权限规范

状态：2026-10-05 确认，约束后续开发；**现有六级权限实现保留不动，不做迁移**。
本文是新功能的开发规范，不是对服务器当前权限行为的重述，也不授权修改现有账号或正式数据。
旧系统功能正常即可长期共存，不列为默认迁移任务，不设清理期限。

## 目标与适用范围

本 MUDLIB 采用 Git 开发、审查、测试和部署，新开发不再以多人在线编辑源码、按巫师等级或个人目录划分开发权限为目标。新增功能与架构重构直接面向简化体系，不为旧权限模型新增兼容分支、别名或双轨授权机制；维护现有功能则保留其原有授权行为。

这项取舍仅针对历史权限架构，不取消游戏功能与存档的正确迁移要求，也不改变驱动最低版本。`mudcore` 仍提供通用机制，由宿主决定人员角色和资源策略，不内置本游戏的两角色规则。

## 人员、对象与开发权限分离

| 层次 | 目标规则 |
| --- | --- |
| 玩家 | 正常游戏，不获得管理命令、任意文件或其他玩家存档的访问能力 |
| 管理员 | 新功能以 `wizardp(me)` 判断管理身份，不再细分巫师等级；高危操作仍校验调用者并记录审计信息 |
| 开发贡献者 | 通过 Git 分支、审查和测试提交代码；仓库贡献身份不等于实服管理员 |
| UID / EUID | 保留对象所属身份与当前执行身份，用于运行期授权；不是人员职级 |

不再将 `(immortal)`、`(apprentice)`、`(wizard)`、`(arch)` 作为新功能的权限层级。只有出现明确的受限运营需求时才另行设计 GM；当前不增加第三类角色、通用 RBAC 平台或逐人逐目录权限矩阵。

## 复用驱动巫师标记

`wizardp(ob)` 判断对象是否具有驱动的巫师标记，本身没有多级权限。`enable_wizard()` 给执行它的当前交互对象设置标记，`disable_wizard()` 清除标记；它们不修改 UID/EUID，也不写入本库的旧角色配置。依据见 FluffOS 的 [wizardp](../../fluffos/docs/efun/mudlib/wizardp.md)、[enable_wizard](../../fluffos/docs/efun/mudlib/enable_wizard.md) 文档及[驱动实现](../../fluffos/src/packages/core/efuns_main.cc)。

新功能直接复用 `wizardp(me)` 区分玩家与管理员，不必再查询旧 `(admin)` 角色名称或比较等级。标记授予与撤销须由可信身份流程控制，不能因玩家参数、显示称号或任意业务请求开启；身份判断仍不替代调用者、文件访问、数据归属及具体操作的安全检查。

当前 [enable_player()](../../feature/command.c) 会为多个旧巫师等级启用该标记。因此，新功能将这些已标记身份视为同一管理类别，但旧命令的等级要求、命令搜索路径和授权行为继续保留；不能将 `wizardp()` 解释为当前旧体系中已经具有 `(admin)` 等级，也不据此自动提升旧账号或批量放宽旧功能。

## 开发和部署边界

- 源码改动在开发环境完成，经 Git 审查和测试后部署；新功能不提供 `ed`、编辑/复制/删除源码等在线开发入口。旧命令本次不删除或禁用，但不再作为日常开发流程。
- 角色权限不会代替部署账号的操作系统权限。运行服务仅获得业务所需的读写范围；源码写入属于部署流程，存档、日志和生成数据属于运行期资源。
- 管理员仍可执行受控的更新、重启及必要运营操作。`eval`、物品发放、玩家数据修改等高危能力不能因“代码已经审查”而绕过授权或审计。
- 新内容按业务模块和共用资产组织，不因历史巫师目录所有权复制同一物品、房间或逻辑。

## 保留的运行期安全

1. 保留 UID/EUID、对象归属与 `valid_read`、`valid_write`、`valid_seteuid` 等安全边界；Root、Domain 等服务身份不映射为玩家职级，不把所有对象统一赋予 Root。
2. 玩家只能通过合法业务流程保存或恢复自己的数据；受信任服务按职责处理共享数据。公开源码不意味着配置、密钥、日志和存档也可公开。
3. 授权来自可信账号及调用上下文，不来自角色显示名称、玩家参数、网络载荷或任意对象属性；未知角色或未知权限要求拒绝受保护操作。
4. 权限判断集中在安全入口，业务表达“是否允许此管理操作”，不继续散布 `wiz_level() >= 3/4/5` 等序号比较。简化层级不等于将校验函数改为无条件放行。

## 与现有实现共存

当前 `securityd.c`、命令搜索路径及部分玩法仍依赖六级体系；现有接口见 [SECURITY_D 当前实现说明](../daemons/securityd.md)。保留这些代码和配置，不进行账号转换，也不要求先完成全库权限重构再开发新功能。

- 新玩家功能使用正常玩家命令或业务入口；新管理员命令放在 `/cmds/adm/`，使用 `wizardp(me)` 判断管理身份并保留调用者约束。无需为新功能追加旧 `(admin)` 角色或中间等级检查；身份成立不代表任意对象都能代替玩家调用命令。
- 复用现有安全精灵的集中授权、身份与文件规则，不另建角色存储、授权引擎或新旧映射层。既有显式命令授权仍按现有实现运行，新功能不增加逐人授权或中间等级扩展。
- 旧接口、目录名称和现有等级判断可以继续存在；这不要求新功能为每个旧等级分别设计行为。维护旧功能时不顺带改权限，也不因新规范撤销现有有效校验。
- 新功能测试至少覆盖未启用巫师标记的玩家被拒绝、启用标记的管理员可执行及调用者校验；涉及数据或文件时，再验证对应归属和读写限制。保留旧命令原权限的回归，不得将新功能通过称为全库权限迁移完成。

## 何时重新评估迁移

不因旧代码年代、等级数量或追求形式统一而迁移。只有遇到具体问题时才评估，例如旧规则导致反复出现的越权风险、明显阻碍新功能接入，或集中改造能显著减少长期维护成本；先比较局部修复与迁移方案，收益须足以覆盖改造、验证和上线风险。

这些情形仅触发评估，不自动授权迁移；没有明确收益就继续共存，不为暂不发生的迁移预建框架或兼容层。

若之后确认迁移旧体系，须另行确认范围，统一处理角色配置、命令路径、授权和等级依赖，明确账号转换并保留游戏数据。不能只缩短 `wiz_levels` 数组：现有 `get_status()` 会将未识别名称归为玩家，可能使遗留最低等级检查被意外放宽；也不能将所有旧巫师自动提升为管理员。

上述简化规范不授权迁移正式账号、目录策略或旧命令等级要求。2026-10-07 的定向修复只在可信 `enable_player()` 普通玩家分支撤销驱动巫师标记，并为 `quest2 <id> <编号> -s` 补齐同等管理校验；六级体系、UID/EUID 和命令路径保留。身份/任务隔离回归覆盖真实连接上的标记刷新、目标与调用者分离、自查与他查；并不代表旧权限体系已迁移。
