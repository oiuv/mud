# 任务奖励结算

本文说明铁匠乾坤石、宝镜里程碑与运送任务的奖励交付顺序及失败处理。

## 铁匠任务

`_0_smith.c` 接入 mudcore 的可选 `try_reward(player, npc)`：乾坤石实际移入玩家后，才调用原 `GIFT_D->work_bonus()` 发经验、潜能和阅历。移动拒绝时销毁候选、提示整理行囊，待办与进度保留，不发数值。回调成功后框架标记完成并保存，因此保存包含数值奖励和完成状态。

`try_reward()` 当前仅用于没有收集物品要求的铁匠任务。框架仍可能在条件检查前收取其他任务的物品；这些收集动作及回调内部异常副作用不自动回滚。旧 `reward()` 的先完成后发奖顺序不变，详见 [框架任务契约](../../mudcore/docs/quest.md)。

## 宝镜任务

`set_task.c` 先算下一次计数；100/200/300/400/500 次沿用原四选一奖池与等概率。抽奖前用奖池内最大重量检查剩余负重，再创建候选并检查实际 `move()`。预检或移动拒绝均保留交还物、轮次、计数及标记，不给数值或银两；整理行囊后可重交，不把奖品扔地上。

负重计算包含手中的待交物，玩家须能容纳奖池中最重的奖品才可抽奖。只有实物交付成功后才执行原数值、银两、失物销毁与轮次更新；第 500 次成功后清零。

## 运送任务

`deliver.c` 每次接受货物时立即通过原 `GIFT_D->bonus()` 结算经验、潜能和阅历，再销毁货物；没有尚未到账的延迟奖励表。延迟对白与任务收尾不再持有玩家资产。正常 `quit` 的保存可保留已到账数值，断线、昏迷也不会让延迟函数丢弃奖励。

每次交货独立计算随机奖励、经验衰减、潜能上限和整数舍入，以交货时的玩家状态为准。

## 验证与部署

定向入口：`node tools/tests/test_identity_quest_rewards.mjs`；`--baseline` 使用 `95cb63b1` 的原实现及其 mudcore 版本做负对照，预期失败。此套件已接入 `node tools/test_gameplay.mjs`。只复制源码到临时目录，使用本机随机端口、测试角色和临时存档；不接触正式数据或模型。

框架新回调与宿主铁匠实现必须成套部署；先记录并备份正在运行的主库和 mudcore 版本、正常保存玩家，再更新匹配的子模块。建议维护窗口重启，避免旧任务 daemon、玩家继承程序或已创建的运送任务仍驻留。仅更新铁匠而保留旧框架会跳过奖励，不能这样部署。

回退须恢复匹配的主库与子模块并重启，保留运行期间新增的玩家进度；代码回退不会补偿已发放或丢失的奖励。
