## 2. 零延迟调度：核对实际 328aaf10

基线为正式采集所用 `fluffos 20260929-5270e7d6-328aaf10`。本次工作树 FluffOS HEAD 是 `ffbd54a6`，因此以下结论取自 `git -C fluffos show 328aaf10:<路径>`，不是以当前 HEAD 或历史 `doc/` 代替运行驱动。

1. `src/packages/core/call_out.cc:146–154,204–208` 将零延迟加入当前 gametick 的事件队列，不同步调用第二掌。
2. `src/backend.cc:56–62,82–102` 区分两种入口：已经在 tick 分发中，新零延迟事件在本批已取出的事件执行完之后继续派发；来自 socket／walltime 的零延迟事件，则等下一次 gametick 才被取出。
3. `src/backend.cc:53,119–122,147–149` 使用按 tick 排序的 multimap，处理后才递增当前 tick；没有执行代码中的随机打乱，只有 TODO。`src/packages/core/heartbeat.cc:35–47` 在每轮心跳开始即排入下一轮心跳，并保留角色心跳顺序。
4. 在本次 1000／1000 ms 配置下，上一轮已排好的下一轮心跳，可以位于后来外部玩家命令排入的第二掌之前。若招式来自本轮心跳中的原 NPC 行为，已在本批且尚未执行的其他角色心跳也能先结束，第二掌才进入下一次取队列循环；目标是否已经轮过心跳仍必须实际观察。
5. 被销毁的参数对象在 `call_out.cc:279–283` 转为零。第二掌所属对象是技能程序，不是目标；不能把目标销毁等同于技能回调被自动取消。

所以“`call_out(0)` 一定先于目标下次心跳”与“零延迟固定等一秒”都不成立。实际入口相位、心跳是否到期、角色是否已在心跳队列中，决定这一窗口。

## 3. 目标失活：普通 USER 路径可以自然形成

第一掌的[原入口](../../kungfu/skill/fireice-strike/binghuo.c#L12)要求目标为人物、双方交战且目标 `living`；没有目标气血必须高于某个正数的条件。[公共 perform](../../cmds/skill/perform.c#L101)及[技能分发](../../inherit/skill/skill.c#L109)也没有增加这一阈值。因此明确准备 `qi=1`、精神正常、仍存活的真实 USER，不会仅因低气血被第一掌拒绝。该初值只是待采实验前提，不代表自然培养已完成。

在无特殊防御映射、无护甲／手套回调、无附毒、施术者 `jiali=0` 的普通路径中：

1. 原第一掌判定成功后，[先令双方忙乱 1、扣 300 内力并调用原直伤](../../kungfu/skill/fireice-strike/binghuo.c#L55)。等级大于 150 才安排第二掌。失败或九阳分支不能计入第二掌守卫分母。
2. 原 [`do_damage()`](../../adm/daemons/combatd.c#L980) 经 `receive_damage/receive_wound` 处理伤害；这两个[资源接口](../../feature/damage.c#L26)把负值截到 `-1` 并开启心跳，不在这个普通直伤同步栈调用昏迷／死亡。必须以实际伤害后的负气血为准，不能把第一掌“判定成功”直接等同于已击昏。
3. 原[角色心跳](../../inherit/char/char.c#L104)先检查负气血／精神，再处理忙乱。因此心跳先到时，即使仍忙乱 1，也会调用原 `unconcious()`；普通 USER 经[原昏迷处理](../../feature/damage.c#L170)停用人物、气血／精神置零，通常留在原房间。
4. 后续原 `perform2()` 先过[对象及同场检查](../../kungfu/skill/fireice-strike/binghuo.c#L79)，再因 `!living(target)` 返回，尚未执行第二掌随机判定及扣费。应记录第一掌消耗与第二掌未进入费用段，不能把零新增费用写成“第二掌命中”。

此路径不需要手工调用 `heart_beat()`、`unconcious()`、`die()` 或移动目标，也不需要修改零延迟。它仍是**待真实观察的源码可达路径**。

NPC 必须另行区分：普通继承者可以昏迷；[林朝英](../../kungfu/class/gumu/lin.c#L189)、[小龙女](../../kungfu/class/gumu/longnv.c#L235)、[杨过](../../kungfu/class/gumu/yang.c#L260)覆盖 `unconcious()` 为 `die()`，其实际死亡／销毁可能让第二掌命中前一个对象缺席守卫，而非 `!living` 守卫。USER 死亡迁往死亡场景、NPC 销毁和普通昏迷不能合并成“离场”。这些不同原 NPC 不纳入本次新增矩阵。

## 4. 离场：已核正常链路的限制

- 第一掌成功时双方的整数忙乱为 1。原直伤虽调用 `target->interrupt_me(target, ...)`，但[原整数忙乱恢复逻辑](../../mudcore/inherit/action.c#L52)在此参数下保留这个忙乱；不能假设直伤已经取消它。
- 目标下一次心跳若没有昏迷，进入忙乱分支并减为 0；同一心跳不再进入 `else` 内的自动逃跑／普通攻击。依据[原心跳](../../inherit/char/char.c#L120)与[原 continue_action](../../mudcore/inherit/action.c#L36)，普通 `wimpy` 不能仅靠这一次忙乱倒数保证抢在第二掌之前离场。
- [`go`](../../cmds/std/go.c#L48)拒绝忙乱者，`do_flee()` 仍调用同一个移动入口。两次网络命令之间不能假定能插入一段“心跳已清忙乱、但本批第二掌尚未执行”的 socket 回调；驱动正在同步派发该批事件。
- NPC 在忙乱减为零后仍可能进入 `scan()`／`chat()`，不是整轮心跳提前返回；[原聊天分发](../../inherit/char/npc.c#L371)此时选择战斗闭包而不是平时的随机走动。已核古墓四位教师的原战斗列表没有直接 `go/flee/random_move` 闭包，也没有主动施展 `strike.binghuo` 的闭包；杨过虽已学烈焰寒冰掌，实际激发和五条战斗闭包不是该招。不能给 NPC 增加新闭包来冒充原自然行为。
- 上述有限核查不覆盖所有场景定时器、特殊武学或其他 NPC 的移动回调。查不到原闭包不证明游戏全局不可达，也不能据此把离场候选标为已验收或移除。

## 5. 后续最小自然观察建议（未实施）

优先保留两项候选的独立状态，不建立全排列；当前只有失活项有足够明确的准备依据。

1. 复用旧 200 级合法第一掌配置，保持原随机及原命令；目标为没有特殊防御／移动覆盖的真实 USER，准备低正气血、正常精神并确认仍存活。施术者初始内力至少 900，以免把第一掌扣费后的内力不足误作失活守卫；不补资源或跳过失败样本。
2. 只对新候选放行目标的原心跳，不能沿用旧单招抑制心跳的结论。保留原命令的**外部玩家输入相位**：现有 `connected → call_out(start,0) → advance → perform_sample` 批量链是在 tick 回调中施招，仅改 `strategy()` 放行并不保证目标心跳先于同轮第二掌。应复用现有隔离连接提交原 `perform strike.binghuo <目标>`，不靠等待特定 tick、修改计时参数或额外施招策略强行制造次序。
3. 实际准备、原命令即时状态、目标原心跳及第二掌入口分账；记录确切角色对象、对象是否仍存在、场地、`living`、气血／精神、忙乱、实际内力，以及观测先后序号。复用已有第二掌入口、角色终态和资源观察；未知返回仍记未观察，不能由入口记录伪造返回值。若目标已被销毁，保存先前确切身份及对应原终态，不能拿另一个 NPC 或空引用冒充它。
4. 原第一掌失败、未排第二掌、第二掌仍遇到活目标、失活拦截、对象缺席、同场失败与内力不足分别统计。原心跳中的自然攻击／恢复如确实发生，单列其账目，不手工调用攻击或聊天，不把全窗口净差当两掌费用。
5. 离场项先等一个可核对的原正常行为，不以预先移出房间、手工 `move/destruct`、更改 delay/gametick、伪造终态或直接调用 `perform2()` 补齐。未观察到时保持 pending；不以合成用例或新配置的存在替代运行覆盖。
