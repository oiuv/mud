## 上线前值得优先处理的问题

### 1. 交易拒绝和后续失败仍可能丢失资产

`put` 部分堆叠先扣原数量并创建候选，随后才检查是否为容器、是否已满及是否允许放入；提前拒绝没有恢复。真实的移动失败虽有放回逻辑，但这些分支没有走到它。入口和扣量见 [put.c](../../cmds/std/put.c#L28)，提前退出见 [put.c](../../cmds/std/put.c#L67)。普通玩家误把部分钱币放入一件非容器衣物即可触发，非存档异常。

拍卖有三类独立问题：先收买家款再处理佣金与交付，失败不回退；拍品转交第三人后仍保留原售权；循环内未清空买家对象，可能向前一笔的买家结算无人出价的后一笔。证据分别为 [结算顺序](../../adm/daemons/auctiond.c#L80)、[物品引用](../../adm/daemons/auctiond.c#L145)、[循环买家解析](../../adm/daemons/auctiond.c#L51)。

其中小额交易佣金为零，会被已经加严的 [公共付款检查](../../adm/daemons/moneyd.c#L108) 拒绝。这是必须补齐的调用方处理，不应恢复零额或负额付款。当前普通玩家 [auction 入口](../../cmds/usr/auction.c#L35) 可按需加载守护进程；没有预加载不等于功能不可达。

### 2. 周期活动可能重复提供成长收益

无量山每次都登记当前游戏月份的十五日二十三时，而触发结束又原样登记。该时刻过去后，后续事件检查仍满足到期条件，可能持续重复抽奖：常见分支增加有上限的实战体会，稀有分支直接增加战斗经验和潜能，并非每次都中奖。源头见 [wuliang.c](../../adm/daemons/event/wuliang.c#L8)、[重新登记](../../adm/daemons/event/wuliang.c#L104) 和 [事件比较](../../adm/daemons/eventd.c#L49)；`at_after()` 只逐字段相加/取绝对值，没有推进到下一个有效日期，见 [eventd.c](../../adm/daemons/eventd.c#L104)。

这里的时间是**游戏历法**，周期是 EVENT_D 的实际心跳，不是现实每月十五日或“每秒无限循环”。修复应明确下次触发时间，不能只降低奖励掩盖重复触发。

同一日期接口还存在跨月不进位、次月首日活动提前的问题，详见世界报告 WL-04；修复日期进位不自动解决再次登记过去时点，需要分开验证。

### 3. 已完成任务与实物交付之间存在缺口

宝镜阶段奖励未检查 `move()` 成功便提示领取，500 次还先清计数。见 [set_task.c](../../adm/daemons/task/set_task.c#L295)。普通移动在负重不足时会拒绝，见 [move.c](../../feature/move.c#L104)。完成一万次打铁的不可重复任务也可能因此失去乾坤石，详见世界报告。

送货任务先销毁提交物，再延迟发奖；回调先删除待发奖励，再因角色已退出销毁或昏迷而直接返回，见 [deliver.c](../../clone/quest/deliver.c#L347) 与 [do_bonus](../../clone/quest/deliver.c#L390)。这类缺陷应围绕“交付成功才完成”或可恢复的待领奖状态解决，不需要先做全任务框架重写。

### 4. 部分武学数值来自错误状态，而非平衡选择

玉箫剑法“极意”的五项数值在共享技能对象初始化时用 `this_player()` 和随机值计算；后续 `query_action(me, ...)` 只选择已有记录，不用当前施招者重算。首次加载者会影响其他角色，见 [初始化](../../kungfu/skill/yuxiao-jian.c#L137) 与 [动作选择](../../kungfu/skill/yuxiao-jian.c#L170)。这会污染任何平衡比较，应先恢复按实际角色计算的语义。无当前玩家首次加载的异常风险尚未在隔离驱动复现，不与已确认的数据冻结混为一谈。

另有胡家刀法检查 200 内力却扣 220，以及回风落雁剑练习检查 30 内力/35 气血却扣 50/40，见 [cang.c](../../kungfu/skill/hujia-daofa/cang.c#L37)、[luoyan-jian.c](../../kungfu/skill/luoyan-jian.c#L109)。持针时普通攻击按剑法、默认绝招却按 `pin` 分发，也属于接口错配，不宜解释为针系应当较弱，见 [perform.c](../../cmds/skill/perform.c#L101)。

### 5. 身份变更需要同步驱动状态

在线降为玩家会重建命令路径，却未清除巫师标记，见 [promote.c](../../cmds/arch/promote.c#L25) 和 [enable_player](../../feature/command.c#L145)。驱动 `wizardp()` 读取独立标志，不会自动根据游戏等级修正，见 [FluffOS 实现](../../fluffos/src/packages/core/efuns_main.cc#L3140)。

影响不是“降权后还能执行所有管理命令”，而是仍可到达且仅按 `wizardp()` 判断的分支残留权限。此外任务查询的一个管理语法漏检身份，见 [quest2.c](../../cmds/usr/quest2.c#L258)。修复这两处不要求迁移现有六级权限体系。

## 架构梳理：应在哪里维护不变量

目前项目并非所有业务集中在一个守护精灵里。命令、通用 feature、守护进程和内容对象共同完成一笔操作；仅修公共函数，不能保证每个调用方都正确处理失败。

```text
玩家输入 → 命令/房间或 NPC 动作 → 业务守护精灵/内容对象 → 角色和物品状态
                                ├─ 钱物交付、奖励、忙乱、装备
                                └─ 存档或异步任务

NPC 问话 → AI_NPC_D → AI_CLIENT_D → UDP 分发 → NPCService → Runner
                                                        └─ Tool / Skill / Hook
                                      ← 玩家正文 ← 校验与业务提交

幻境冻结事实 → 创作请求 → 世界队列 → Runner → 数据库结果 → 原子发布
幻境房间显示 ← 身份匹配的正文快照；未就绪时仍用规则描写
```

### 角色和物品

共享移动层负责重量、环境、装备和幻境准入，不知道一次移动是否代表拍卖成交或任务已领奖。因此业务不能忽略返回值，也不能把“对象存在”当作所有权凭据。游戏通用层宜保持小而明确的契约，交易和任务自行负责各自的成功顺序。详细责任链已分别写入经济与世界报告。

### 战斗和武学

兵器类型决定基础武学映射、默认动作及部分装备限制；实际攻防仍经过角色属性、动作数据、伤害类型、武学特殊回调和临时状态。共享技能对象应保存定义，按角色变化的临时值应在调用中计算或绑定到角色，不应留在共享初始化/恢复状态中。兵器报告分别追踪装备、普通攻击和绝招链，避免只看一张伤害表。

### AI：入口、推理、提交彼此分开

本轮检查了三条连续链，未在这些已读分支确认新的实现缺陷；这不是全 AI 服务或实际回答准确率的保证。

1. **连接与投递**：`AI_NPC_D` 保存原连接对象并在存活检查和投递前复核，见 [ai_npc_d.lpc](../../adm/daemons/ai_npc_d.lpc#L83)。Python 服务使用独立工作容量和长请求租约，取消或过期后不发送正常终态，见 [udp_server.py](../../ai/src/udp_server.py#L262)。重连回归检查的是旧回复不能误投，不要求 NPC 永久忘记已有成功对话。
2. **工具与指导**：Runner 统一循环，Tool 在 Hook 修改参数前后都校验授权，见 [tools.py](../../ai/src/runtime/tools.py#L148)。Skill 目录只注入获准名称和说明，由同一入口加载正文/参考资料；Skill 可收窄工具集合，不能扩大授权，见 [skills.py](../../ai/src/runtime/skills.py#L104)。Hook 的观测与干预职责分开，见 [hooks.py](../../ai/src/runtime/hooks.py#L24)，不是额外业务执行器。
3. **业务完成**：Runner 产出可提交候选，不立即宣告持久化成功；提交前复查候选、权限、取消和业务验证，见 [runner.py](../../ai/src/runtime/runner.py#L253)。NPC 在单事务内保存正文、关系与去重结果，见 [service.py](../../ai/src/npc/service.py#L236)。世界任务先核对版本/尝试租约，再保存结果并用临时文件替换发布，见 [store.py](../../ai/src/world/store.py#L259) 与 [publish](../../ai/src/world/store.py#L299)；LPC 再比对世界、坐标和摘要，见 [illusion_content_d.lpc](../../adm/daemons/illusion_content_d.lpc#L78)。因此“已受理”不能显示成“已完成”。

**部署边界**：默认 AI 地址为 `127.0.0.1`，见 [settings.py](../../ai/src/settings.py#L22)。当前 UDP 层校验格式、请求关联和租约令牌，不提供网络客户端身份认证；`memory` 接口按载荷中的 NPC/玩家标识查询，见 [service.py](../../ai/src/npc/service.py#L106)。这些令牌不是客户端登录凭证。不能把服务未经访问控制地绑定公网，再指望 Tool 权限防止伪造问话或查询记忆；远程部署需由可信网络边界限制访问。本轮未读取实际部署配置，不认定正式服已暴露。

## 兵器体系的下一步，不立即实施

十二类兵器已经有用途与武学差异，但五个标志并不等于五套通用被动：当前 `TWO_HANDED`、`SECONDARY` 用于手位；`EDGED`、`POINTED`、`LONG` 尚未成为公共战斗被动。不能仅凭名称就宣称已有破甲、穿刺或距离优势。详见兵器报告的实际消费者及十二类对照。

建议顺序：

1. **修正数据取值和资源守恒。** 先消除跨角色冻结、门槛低于实扣和分发错配，否则数值评测会比较错误的实现。
2. **建立同条件战斗基线。** 控制经验、基础/特殊武学、属性、武器品质、内功加力、防具、对手与随机样本；分开普通攻击和绝招，比较有效伤害、命中、控制占比、内力效率、自忙和生存，而非只比较 `damage`。
3. **小步试验通用特性。** 可先选长兵器与短兵器的进攻/贴身取舍、利器与钝器面对不同防护的取舍。每次只引入一个有代价的差异，并保留对照；不先叠加所有五标志，也不把长兵器等同于远程武器。
4. **再校准具体武学。** 类别特性与门派绝招可能相乘，先检查多段攻击、命中回调、固定伤害和减伤绕行。保留棍与杖两类，不顺带重做分类或迁移玩家技能。

本轮没有足够的等条件统计支持“某类最强”“所有兵器已平衡”或具体加减百分比；报告中的公式差异只是后续样本选择依据。
