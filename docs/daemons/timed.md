# TIME_D — 宿主游戏时钟

`adm/daemons/timed.c` 继承 mudcore 的 `CORE_TIME_D`，保留时间显示、现实／游戏计划任务接口，
在宿主层负责游戏时间连续性。没有修改 mudcore 通用实现，也没有增加玩家调时命令。

## 时间推进

首次遇到没有锚点的旧记录，沿用旧公式在启动时刻计算的初始显示日期。
随后按以下关系推进，不再累计心跳次数或在重启时重新取模：

```text
当前内部游戏秒数 = game_anchor + (当前现实秒数 - real_anchor) × DATE_SCALE
显示年份 = 内部公历年份 - 1970 + calendar_era
```

`DATE_SCALE` 仍为 60，即现实一秒对应游戏一分钟。心跳调用原现实时间处理和游戏时间处理；
心跳延迟不会丢失经过时间。内部月份、闰日及现有时区保持不变，不能用显示纪年判断闰年。
显示日期由最近一次心跳更新，`query_gametime()` 则按调用时的现实秒数计算。

## 保存与恢复

复用公共数据库 `data/dbased.o` 中宿主对象的记录：

| 字段 | 含义 |
| --- | --- |
| `clock_version` | 当前锚点格式版本，值为 1 |
| `real_anchor` | 建立锚点时的现实秒数 |
| `game_anchor` | 对应内部游戏秒数 |
| `calendar_era` | 正纪年偏移，跨年自动递增 |
| `gametime` | 保存时的当前内部秒数，保留原有记录字段 |

首次建立锚点即通过既有数据库落盘；以后恢复有效锚点，不根据旧 `gametime` 猜测保存时刻。
重启计入停服经过时间，正常保存仍沿用公共数据库机制。系统时间是推进依据，应保持服务器
时钟准确；这不是独立单调时钟或历史时间修复工具。

无量山活动启动后只登记未来下一场，不补发停服期间各月奖励；其他活动仍使用各自既有周期。
活动登记与日期进位见 [EVENT_D](eventd.md)。

## 验证与部署

`node tools/tests/test_world_events.mjs` 在隔离 MUDLIB 中替换宿主的现实时间输入，
验证初次落盘、1∶60 速率、跨年／闰月、数据库恢复和独立驱动进程重启；不修改正式数据。

部署前备份 `data/dbased.o`，先结束或取消现有拍卖，再按正常维护流程更新并重启。
本次不改玩家存档。回退旧代码会恢复旧固定纪年与重启重置行为；不要把回退当作时间连续性保证，
也不要为了回退时钟而直接覆盖正在运行的整个公共数据库。
